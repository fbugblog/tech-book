# 第1章 LLMアプリケーションフレームワークの解剖

LLMアプリケーションの開発では、奇妙な逆転が起きる。動くものを作るまでは驚くほど速いのに、そこから精度を上げ、本番に載せる段階で急に手が止まる。原因の多くは、プロトタイプを速く作るために使った抽象化が、そのまま改善の障害になっていることにある。この章では、フレームワークが何を引き受けてくれるのか、その代わりに何を見えなくするのかを整理し、LangChainとLlamaIndexという二つの代表的な選択肢の設計思想を突き合わせる。

## 1.1 なぜフレームワークが必要か——抽象化の効用と代償

LLMのAPIを叩くだけなら、フレームワークは要らない。HTTPクライアントとJSONのパーサーがあれば足りる。それでもフレームワークが使われるのは、実務のLLMアプリケーションが「APIを1回叩く」処理ではないからだ。

現場で必要になるのは、たとえば次のような部品である。

- 複数のモデルプロバイダーの差異を吸収する層。Claude、GPT、Geminiでは、ツール定義のスキーマもストリーミングのイベント形式も、マルチモーダル入力の渡し方も異なる
- プロンプトをテンプレートとして管理し、変数の埋め込みと履歴の差し込みを型安全に行う層
- 文書を読み込み、分割し、埋め込みベクトルに変換し、ベクトルストアに出し入れする一連のパイプライン
- リトライ、フォールバック、タイムアウト、レート制限への対処
- ストリーミング、非同期実行、バッチ実行を、同じコードから切り替えられる仕組み
- トレースと評価のためのフック

これらは本質的な差別化要因ではない。どのチームが書いても似たものになる。だからライブラリに任せる価値がある。

問題は、フレームワークがここで止まらないことである。多くのフレームワークは、部品の提供に加えて「よくあるユースケースを1行で実現する」高水準の抽象化も用意する。かつてのLangChainの `RetrievalQA` や `ConversationalRetrievalChain` がその典型だった。

```python
# かつての高水準チェーン。中で何が起きるかはドキュメントを読まないと分からない
qa = RetrievalQA.from_chain_type(llm=llm, retriever=retriever, chain_type="stuff")
answer = qa.run("就業規則では有給休暇の繰り越しはどうなっている？")
```

この2行の内側では、少なくとも次の処理が起きている。質問文をそのまま埋め込みベクトルに変換し、ベクトルストアから既定の件数（多くの場合4件）を取得し、取得した文書を改行で連結し、ライブラリに組み込まれた英語のプロンプトテンプレートに流し込み、LLMに渡す。

精度が出なかったとき、直すべき箇所はこの中に何箇所もある。取得件数が足りないのか、質問文の表現が文書の表現と噛み合っていないのか、連結した文脈が長すぎて中盤が無視されているのか、英語のプロンプトが日本語の応答品質を落としているのか。ところが呼び出し側のコードは `run()` の1行しかなく、どこを触ればよいのかの手がかりがない。これが「ブラックボックス化の罠」である。

> 抽象化は、中身を知っている人にとっては省力化であり、知らない人にとっては迷路である。

この反省から、現在のLangChainとLlamaIndexはどちらも、モノリシックな高水準チェーンを主役の座から降ろし、**小さな部品を明示的に組み合わせる**方向へ設計を寄せている。LangChainはLCELとLangGraph、LlamaIndexはQueryEngineの構成要素の分解とWorkflowsがそれにあたる。本書がこの二つを軸に据えるのも、同じ理由による。

実務での判断基準は単純だ。**組み立ての手順が読めない抽象化は、本番のコードでは使わない。** プロトタイプで1行のヘルパーを使うのは構わないが、精度を詰める段階に入ったら、そのヘルパーが何をしているかを部品のレベルまで開き、明示的に書き直す。この書き換えのコストは、精度改善のたびにブラックボックスの中を推測して回すコストより、ほぼ確実に小さい。

## 1.2 LangChainとLlamaIndexの設計思想

二つのライブラリは機能の重なりが大きく、「どちらを使うべきか」という問いは頻繁に出る。だが機能一覧を並べて比べても答えは出ない。見るべきは、それぞれが**何を中心概念に置いたか**である。

### LangChain——「処理の連鎖」が中心

LangChainの中心概念は `Runnable` である。入力を受け取り出力を返すあらゆる処理を、同一のインターフェースに揃え、それらを連結して1つの大きな `Runnable` にする。プロンプトもモデルもパーサーも検索器も、すべてこの型に収まる。つまりLangChainが最初に解いた問題は「LLMを含む処理をどう合成するか」であり、データの扱いはその上に載る応用の一つという位置づけになる。

この思想は現在も一貫している。1.0系ではエージェントの構築が `create_agent` に集約され、その実行基盤としてLangGraphが下に敷かれた。状態を持つループ処理という、単純な連鎖では表現しきれない領域に、中心概念が一段拡張された形である。

### LlamaIndex——「データとの接続」が中心

LlamaIndexの中心概念は、名前のとおり**インデックス**である。手元のデータをLLMから引ける形に構造化することを出発点に置き、そこから逆算してAPIが設計されている。`Document` と `Node`、それを作る `NodeParser`、引き当てる `Retriever`、引き当てた結果を加工する `NodePostprocessor`、最終的な文章に仕立てる `ResponseSynthesizer`——RAGの各工程に対応する名前付きの役割が、最初から分解された形で用意されている。

データコネクタの層の厚さも、この思想の反映である。LlamaHubには各種SaaS、データベース、ファイル形式に対する読み込み実装が集まっており、「社内のあのシステムから文書を引いてくる」という、退屈だが避けて通れない作業の初期コストを下げる。

### 比較と使い分け

| 観点 | LangChain | LlamaIndex |
| --- | --- | --- |
| 中心概念 | `Runnable` による処理の合成 | データのインデックス化と検索 |
| 得意な領域 | 汎用のチェーン、エージェント、状態遷移 | RAG、文書の構造化、多様なデータソース接続 |
| RAGの抽象度 | 部品を自分で組む前提 | 役割が名前付きで分解済み |
| エージェント | LangGraphによる状態遷移機械 | Workflowsによるイベント駆動 |
| 迷ったときの使い道 | 制御フローが複雑なとき | 検索の質を詰めたいとき |

実務では、二者択一にしないという答えが最も多い。**検索層をLlamaIndexで組み、その検索器をLangChainのツールとしてエージェントに渡す**構成は、両者の得意領域が素直に噛み合う。LlamaIndexのクエリエンジンは呼び出せば文字列を返すだけなので、LangChainのツールとして包むのに特別な仕掛けは要らない。

```python
from langchain_core.tools import tool
from llama_index.core import VectorStoreIndex

index = VectorStoreIndex.from_documents(documents)
query_engine = index.as_query_engine(similarity_top_k=8)

@tool
def search_internal_docs(query: str) -> str:
    """社内規程・手順書を検索して、根拠となる記述を返す。"""
    return str(query_engine.query(query))
```

逆に避けたいのは、同じ役割の抽象化を二重に重ねることである。LlamaIndexのクエリエンジンをLangChainのリトリーバーで包み、さらにそれを高水準チェーンに渡す、といった構成は、エラーが起きたときに追うべき層が増えるだけで得るものがない。**層を足すときは、その層が何の責務を引き受けるのかを言えるかどうかを基準にする。**

## 1.3 LCELの宣言的データフローを読む

LCEL（LangChain Expression Language）は、`Runnable` を `|` 演算子でつなぐ記法である。見た目はシェルのパイプに似ているが、やっていることはパイプよりも踏み込んでいる。

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_anthropic import ChatAnthropic

prompt = ChatPromptTemplate.from_template(
    "次の文脈だけを根拠に質問へ答えよ。文脈にない場合は「分からない」と答えよ。\n\n"
    "文脈:\n{context}\n\n質問: {question}"
)
model = ChatAnthropic(model="claude-sonnet-5")

chain = prompt | model | StrOutputParser()
```

`|` は実行ではなく**合成**である。この行が評価された時点ではLLMは呼ばれておらず、三つの `Runnable` を順に実行する `RunnableSequence` という一つのオブジェクトができただけだ。実行は `chain.invoke({"context": ..., "question": ...})` を呼んだときに初めて起きる。

この「まず構造を組み立て、あとで実行する」という宣言的な設計から、三つの実利が生まれる。

**第一に、実行方法を後から選べる。** 合成された `Runnable` は、同期の `invoke`、非同期の `ainvoke`、逐次出力の `stream` / `astream`、まとめ処理の `batch` / `abatch` をすべて備える。チェーンを書いたときに実行方式を決め打ちする必要がなく、Web APIのハンドラーからは `astream` で、バッチ評価のスクリプトからは `batch` で、同じチェーンを呼べる。

**第二に、構造が実行計画として見える。** 合成結果はグラフとして取り出せるため、トレースの各ステップがどの部品に対応するかが自動的に決まる。LangSmithのようなトレースツールが特別な計装なしに働くのは、この構造があるからだ。

**第三に、横断的な関心事を後付けできる。** リトライやフォールバックは、チェーンの中に書き込むのではなく、組み上がった `Runnable` に対して宣言する。

```python
robust_chain = (prompt | model | StrOutputParser()).with_retry(
    stop_after_attempt=3
).with_fallbacks([prompt | backup_model | StrOutputParser()])
```

### 分岐と合流を読む

直列だけなら記法の妙味は薄い。LCELが効いてくるのは、入力を複数の経路に分けて並行に処理し、結果を辞書として合流させる場面である。辞書リテラルは暗黙に `RunnableParallel` に変換され、値のそれぞれが並行に実行される。

```python
from langchain_core.runnables import RunnablePassthrough

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)
```

このチェーンの入力は質問の文字列である。それが辞書の二つの値へ同時に渡り、片方は検索を経て整形された文脈になり、もう片方は `RunnablePassthrough` によって素通りして質問文のまま残る。二つが揃った時点で辞書が完成し、プロンプトのテンプレート変数に収まる。

読み方のこつは、**`|` の前後でデータの型がどう変わるかを追うこと**である。上の例なら `str` → `dict[str, str]` → `PromptValue` → `AIMessage` → `str` と変化している。型が合わないときに出るエラーは、この連鎖のどこで期待とずれたかを示していると考えればよい。

任意のPython関数は `RunnableLambda` で連鎖に持ち込める。`|` の連鎖の中に関数を直接書いた場合も、暗黙に変換される。

```python
def format_docs(docs) -> str:
    return "\n\n".join(f"[{d.metadata['source']}] {d.page_content}" for d in docs)
```

### LCELをどこでやめるか

LCELは一方向に流れるデータフローの記述には強いが、**ループと条件付きの巻き戻しには向かない**。「ツールを呼ぶ→結果を見る→必要ならもう一度呼ぶ」というエージェントの循環を、`|` の連鎖で書こうとすると、途端に読めないコードになる。

この境界が、LangChainがLangGraphを別に用意した理由である。一方向のパイプラインはLCELで、状態を持つ循環はLangGraphで。この使い分けは第4章で詳しく扱う。次章ではまず、パイプラインの中身そのもの——RAGの検索品質をどう上げるかに踏み込む。

::: tip この章のポイント
- フレームワークが引き受けるべきなのはプロバイダー差異の吸収、テンプレート管理、リトライといった共通部品であり、組み立ての手順が読めない高水準チェーンは本番のコードから外していく
- LangChainの中心概念は `Runnable` による処理の合成、LlamaIndexの中心概念はデータのインデックス化であり、この違いが得意領域の違いに直結している
- 検索層をLlamaIndexで組み、LangChainのツールとしてエージェントに渡す構成は、両者の得意領域が素直に噛み合う
- LCELの `|` は実行ではなく合成であり、宣言的に組んだ構造から同期・非同期・ストリーミング・バッチの実行方式が後から選べる
- LCELは一方向のデータフロー向けであり、状態を持つ循環はLangGraphの領分である
:::
