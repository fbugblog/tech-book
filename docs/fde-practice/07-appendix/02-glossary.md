# 付録B 用語集

本書で用いた用語を、初出の章とともに並べる。一般的な定義ではなく、**本書での使い方**を書いてある。

## FDEと方法論

| 用語 | 本書での意味 | 初出 |
| --- | --- | --- |
| FDE（Forward Deployed Engineer） | 顧客の業務プロセスの内側に入り、課題発見から本番運用の定着までを一つの責任として引き受けるエンジニア。配置ではなく責任範囲の設計を指す | 第1章 |
| PoC貧乏 | 検証は成功するのに本番に至らない状態が続く症状。原因は多くの場合、技術ではなくPoCの設計にある | 第1章 |
| 差分を設定に追い出す | 顧客ごとの特殊性をコードの分岐ではなく宣言的な設定として外に出し、実装を一つに保つ原則 | 第1章 |
| シャドーIT | 公式のシステムの外で回っている仕組み。部門のExcelマクロ、個人のデータベース、自作スクリプトなど。業務の実態を最も正確に反映する一次資料 | 第2章 |
| 残存作業率 | 自動化しても残る確認や例外処理の割合。ROI試算で削減効果を割り引く係数 | 第2章 |
| 再配置可能性 | 浮いた時間が別の価値ある業務に回る割合。会計上の効果を見積もる係数 | 第2章 |
| Enablement（内製化支援） | 顧客が自分たちで保守・改修できる状態を作る活動。FDEの最終成果物 | 第14章 |
| ADR（Architecture Decision Record） | 設計判断を、選択肢・却下理由・受け入れる制約・見直しの条件とともに残す記録 | 第14章 |

## データ基盤

| 用語 | 本書での意味 | 初出 |
| --- | --- | --- |
| raw層 | 取り込んだ生データを加工せず、取得日時つきで不変のまま保持する層。過去の数字が変わった理由を説明するための保険 | 第3章 |
| quarantine（隔離） | スキーマ検証に失敗した行だけを退避させる領域。捨て場ではなく、直す人へ差し戻すための導線 | 第3章 |
| グレイン（粒度） | ファクトテーブルの1行が何を表すか。一文で宣言できるまで設計を進めない | 第4章 |
| ファクト／ディメンション | 起きた出来事と量（ファクト）と、それを説明する属性（ディメンション）。分析の問いを「量をディメンションで切る」形に統一する | 第4章 |
| 加法的な測定値 | 足し算が意味を持つ指標。金額は加法的だが単価は違う。比率をファクトに持たせると集計階層で誤る | 第4章 |
| SCD Type 2 | ディメンションの変更を新しい行として追加し、有効期間で管理する方式。当時の属性による集計を可能にする | 第4章 |
| Data Vault 2.0 | Hub（業務キー）、Link（関係）、Satellite（属性と履歴）で構成する統合手法。ソースごとにSatelliteを分け、統合の判断を下流に遅らせられる | 第4章 |
| セマンティックレイヤー | 指標と結合の定義を宣言的に持つ層。LLMにテーブルではなくこの層を見せることで、出力を狭いJSONに限定できる | 第4章 |
| staging / intermediate / marts | dbtの三層構成。各層で許される操作を限定し、ソース固有の整形を一か所に集約する | 第5章 |
| 増分モデル | 差分のみを処理するモデル。ルックバック期間と `merge` 戦略で遡及更新に備える | 第5章 |
| 冪等性 | 同じジョブを二回流しても結果が変わらない性質。自動リトライと障害復旧の前提になる | 第5章 |
| exposures | dbtで、データを利用する先（ダッシュボード、アプリ）を宣言する仕組み。障害時の影響範囲を機械的に列挙できる | 第5章 |
| CDC（変更データキャプチャ） | データベースのトランザクションログを読んで変更を捕捉する方式。削除と更新順序を正しく扱える | 第11章 |

## LLMとRAG

| 用語 | 本書での意味 | 初出 |
| --- | --- | --- |
| RAG | 検索で集めた文脈をLLMに渡して回答させる構成。本書では「LLMに文書を渡す仕組み」ではなく検索システムとして扱う | 第6章 |
| チャンク | 検索の単位。本文だけでなく、見出しパス・有効期間・構造化側の業務キーを必ず持たせる | 第6章 |
| 見出しパスの前置 | 埋め込み対象のテキストの先頭に、その節の見出し階層を加える工夫。費用ほぼゼロで検索精度が上がる | 第6章 |
| 想定質問の生成 | 取り込み時に、その一節が答えになる質問をLLMで生成し埋め込みに含める手法。文書の語彙と利用者の語彙の溝を埋める | 第6章 |
| 親子チャンク | 小さい単位で検索し、ヒットした親を大きい単位で渡す構成。検索精度と回答品質の矛盾を解く | 第6章 |
| ハイブリッド検索 | ベクトル検索（意味の近さ）とキーワード検索（語の一致）を併用する構成 | 第6章 |
| RRF（Reciprocal Rank Fusion） | 複数のランキングを順位の逆数で統合する手法。スコアの正規化が不要 | 第6章 |
| リランキング | 質問とチャンクのペアを直接評価し、上位数件に絞る工程。件数を絞ることが生成品質に効く | 第6章 |
| 棄権（abstention） | 根拠が見つからないときに「判断できない」と答える振る舞い。明示的に許可しないとモデルは何かを答えようとする | 第6章 |
| HyDE | 質問に対する仮の回答を生成し、その文を埋め込んで検索する手法。質問文より文書の語彙に近くなる性質を使う | 第6章 |
| GraphRAG | 文書から実体と関係を抽出してグラフを作り、それをたどって回答する手法。網羅性が要る問いに限って検討する | 第6章 |
| 構造化出力 | 出力をスキーマに閉じ込める設計。後続処理のためだけでなく、モデルへの指示を精密にする役割も持つ | 第7章 |
| プロンプトは努力目標、バリデーションは保証 | 指示で期待する挙動と、コードで担保する制約を役割分担させる原則 | 第7章 |
| Tool Use / Function Calling | LLMに関数を渡して呼び分けさせる仕組み。ツールの集合はそのままモデルに与える権限の集合になる | 第7章 |
| プロンプト・アズ・コード | プロンプトをモデル設定とともにファイルで管理し、変更をCIで評価する運用 | 第7章 |

## エージェントと運用

| 用語 | 本書での意味 | 初出 |
| --- | --- | --- |
| エージェント | ループを回して、自分で次の行動を決めるシステム。ループがあることが本質であり、停止条件の設計が課題になる | 第8章 |
| ReAct | 思考・行動・観察を繰り返す推論形式。予期しない結果に強いが、全体の見通しを持たない | 第8章 |
| Plan-and-Solve | 先に計画を立ててから実行する形式。計画を人間がレビューできる利点がある | 第8章 |
| 目的の漂流 | エージェントが元の依頼と無関係な探索を始める壊れ方。各ステップで依頼を再提示して防ぐ | 第8章 |
| Human-in-the-Loop | 人間の承認や修正をフローに組み込む設計。配置は「取り消せるか」で決める | 第8章 |
| 承認疲れ | すべてに承認を求めた結果、承認者が内容を読まずに押すようになる状態。形式的な統制は実質的な無統制と変わらない | 第8章 |
| SSE（Server-Sent Events） | サーバーからの一方向のストリーミング。通常のHTTPのままで企業プロキシを通りやすい | 第9章 |
| 冪等キー | 同じリクエストの二重実行を防ぐ識別子。LLM呼び出しは1回あたりの費用が無視できないため必須になる | 第9章 |
| 検証用UI／運用UI | 仮説を確かめるための使い捨てのUIと、毎日の業務を回すUI。前者の価値は捨てやすさにある | 第10章 |
| ラッパーAPI | 既存システムの前段に置く層。語彙の翻訳・保護・キャッシュ・監査・認可を担う | 第11章 |
| Faithfulness（忠実性） | 回答が、渡した文脈だけから導けるかを測る指標。低い場合はハルシネーションが起きている | 第12章 |
| Recall@k | 正解文書が上位 `k` 件に含まれる割合。低いと、生成をどれだけ改善しても上限が決まる | 第12章 |
| LLM-as-a-Judge | LLMに出力を採点させる手法。位置・冗長性・自己選好のバイアスがあり、判定器自体の検証が必要 | 第12章 |
| 影武者実行（シャドー実行） | 本番の入力を新モデルにも流し、出力は見せずに記録だけする段階。評価データセットに現れない挙動差が見える | 第13章 |
| 間接プロンプトインジェクション | RAGが読み込む文書やメールに指示を埋め込む攻撃。最も効く対策はプロンプトの工夫ではなく権限設計 | 第13章 |
| プロンプトキャッシュ | プロンプトの前方一致部分をキャッシュする仕組み。固定部分を前に集める並び順が前提になる | 第13章 |

::: tip 用語集の使い方
本書は章をまたいだ参照が多い。途中の章から読み始めて前提が分からなくなった場合は、この付録で初出章を引いてから戻ると、必要な箇所だけを読み直せる。
:::
