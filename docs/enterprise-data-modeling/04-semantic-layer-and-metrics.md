# 第4章 セマンティックレイヤーとメトリクス定義

役員会議に三つの「売上」が持ち込まれる、という光景はどこの企業にもある。営業部のダッシュボード、経理のレポート、データチームの分析。どれも間違っていない。前提が違うだけだ。返品を引いているか、社内取引を除いているか、計上基準が受注日か出荷日か。前提が本文に書かれていないので、比べようがない。

この問題は、テーブル設計をどれだけ厳密にやっても解けない。第2章と第3章で作ったのは、あくまで事実の入れ物である。事実から指標を導く規則は、テーブルの外にある。セマンティックレイヤーは、その規則をコードとして置く場所だ。

## 定義はBIツールの中ではなく、リポジトリの中に置く

従来、指標の定義はBIツールの中にあった。ダッシュボードの計算フィールド、レポートのフィルタ条件、Excelの数式。この置き場所には三つの問題がある。

第一に、ツールごとに定義が分裂する。BIツールが二つあれば定義も二つになり、片方だけ修正される。第二に、差分が追えない。誰がいつ定義を変えたのか、GUIの操作履歴からは復元できない。第三に、機械から読めない。LLMにダッシュボードの計算フィールドを読ませることはできない。

セマンティックレイヤーは、これを宣言的な定義ファイルとしてバージョン管理下に置く。実装としてはdbtのセマンティックモデル（MetricFlow）、Cube、LookMLなどが該当するが、本質は製品ではなく、次の三点を一箇所で宣言することにある。

- **エンティティ**：テーブルが何を表し、どのキーで他とつながるのか
- **ディメンション**：どの切り口で分解してよいのか
- **メジャーとメトリクス**：何をどう集約すると、どの指標になるのか

```yaml
semantic_models:
  - name: order_line
    description: 受注明細。一行が一つの注文における一商品の明細を表す
    model: ref('fct_order_line')
    defaults:
      agg_time_dimension: ordered_at

    entities:
      - name: order_line
        type: primary
        expr: order_line_key
      - name: customer          # dim_customer と結合する経路
        type: foreign
        expr: customer_key
      - name: product
        type: foreign
        expr: product_key

    dimensions:
      - name: ordered_at
        type: time
        type_params: { time_granularity: day }
        description: 受注日時。計上基準は受注日であり、出荷日ではない
      - name: sales_channel
        type: categorical
        description: 販売チャネル
        # 取りうる値を明示する。列定義には現れない情報
        meta:
          allowed_values: [ec, retail, wholesale, internal]

    measures:
      - name: net_amount_sum
        agg: sum
        expr: net_amount
        description: 値引後の明細金額。税抜、社内取引を含む
      - name: quantity_sum
        agg: sum
        expr: quantity
      - name: order_count
        agg: count_distinct
        expr: order_id
```

ここまでが「何を集約できるか」の宣言である。指標そのものは、その上に定義する。

```yaml
metrics:
  - name: net_revenue
    label: 純売上
    type: simple
    description: |
      値引後・返品控除後の売上。社内取引（sales_channel = 'internal'）は除外する。
      計上基準は受注日。出荷ベースの数値が必要な場合は shipped_revenue を使うこと。
    type_params:
      measure: net_amount_sum
    filter: "{{ Dimension('order_line__sales_channel') }} != 'internal'"

  - name: gross_margin_rate
    label: 粗利率
    type: ratio
    description: 粗利 ÷ 純売上。分母が0の期間はNULLを返す
    type_params:
      numerator: gross_margin
      denominator: net_revenue

  - name: net_revenue_mom
    label: 純売上の前月比
    type: derived
    type_params:
      expr: "net_revenue / net_revenue_prev"
      metrics:
        - name: net_revenue
        - name: net_revenue
          offset_window: 1 month
          alias: net_revenue_prev
```

この定義ファイルが持つ価値は、「純売上とは何か」という問いへの答えが、レビュー可能な差分として存在することにある。定義を変えるにはプルリクエストが要り、誰がいつ何のために変えたかが残る。経理が計上基準の変更を決めたとき、その決定がコミットとして記録される。

## 単一の真実は、単一のテーブルでは作れない

「Single Source of Truth」という言葉は、しばしば「すべてのデータを一箇所に集める」という意味で使われるが、実務ではそれだけでは足りない。集まった先で定義が分裂すれば、真実は再び複数になる。

有効なのは、テーブルではなく**定義**を一箇所にすることだ。物理的なデータは複数の層に分散していてよい。Raw Vaultにもマートにも同じ事実が存在してよい。しかし、「純売上」という語の定義は一箇所にしかない、という状態を作る。

この状態を維持するには、規律が三つ要る。

**メトリクスは、必ずセマンティックレイヤー経由で消費する。** BIツールがマートのテーブルを直接叩き、独自の計算フィールドを作れる状態を残してはいけない。抜け道があれば必ず使われる。BIツールにはセマンティックレイヤーのAPI経由で接続し、生テーブルへの権限は配らない。

**メトリクスカタログを公開する。** 定義ファイルから、検索可能なカタログを生成する。利用者が探す場所を一つにすれば、「似た指標を自分で作る」という行動が減る。

| 指標名 | 定義 | 所有者 | 除外条件 | 更新頻度 |
| --- | --- | --- | --- | --- |
| `net_revenue` | 値引後・返品控除後の売上 | 経理部 | 社内取引 | 日次 |
| `active_customers` | 過去90日に一件以上の受注がある顧客数 | マーケ部 | テスト顧客 | 日次 |
| `gross_margin_rate` | 粗利 ÷ 純売上 | 経理部 | 同上 | 日次 |

所有者の列が入っている点が重要だ。定義の変更を承認する人を明示しないと、定義は誰のものでもなくなり、なし崩しに分裂する。技術的な仕組みより、この一列のほうが効くことは多い。

**廃止の手順を決める。** 古い指標を消すときは、まず非推奨の印を付け、参照元を洗い出し、移行期間を置いてから消す。非推奨の指標に `deprecated: true` のフラグとメッセージを持たせておくと、クエリ時に警告を返せる。

## LLMにスキーマを渡すための注釈設計

Text-to-SQLシステムの精度は、モデルの性能よりもスキーマの説明品質で決まる場面が多い。BIRDのような現実的なベンチマークで実行精度が伸び悩む主因は、SQLの構文生成ではなく、どの列が何を意味し、どう結合すべきかという知識が欠けていることにある。裏を返せば、この知識をメタデータとして与えることが、最も費用対効果の高い改善策になる。

渡すべき情報を、効きやすい順に並べると次のようになる。

**列の意味と単位。** `amount` が税抜か税込か、通貨は何か、`duration` は秒か分か。これはコメントとして持ち、スキーマと一緒に渡す。

```sql
comment on column fct_order_line.net_amount is
  '値引後の明細金額。税抜・日本円。返品は fct_return に別途記録される';
comment on column fct_inventory_daily.quantity_on_hand is
  '日次の在庫残高。半加法的：日付方向に SUM してはならない。期間集計は平均または期末値を使う';
```

**カテゴリ列の取りうる値。** 前述の `allowed_values` がこれにあたる。実務では定義ファイルに書くだけでなく、実データからプロファイルを取って値の一覧と出現頻度を自動生成し、定義とずれていないかを検証するとよい。ずれていれば、それは上流のスキーマドリフトの兆候である。

**正しい結合経路。** 同じ列名を持つテーブルが複数あるとき、モデルはしばしば誤った経路で結合する。結合できる組み合わせを明示的に列挙するほうが安全だ。

```yaml
join_paths:
  - from: fct_order_line
    to: dim_customer
    on: "fct_order_line.customer_key = dim_customer.customer_key"
    note: |
      dim_customer は SCD Type 2 である。
      現在の顧客属性で集計する場合は is_current = true を付ける。
      受注当時の属性で集計する場合は条件を付けず、そのまま結合する。
```

このnoteのような記述は、人間のレビューにも役立つ。SCD2のディメンションに `is_current` を付け忘れて件数が膨らむのは、人間もよくやる誤りである。

**やってはいけないこと。** 肯定形の説明だけでなく、禁止の明示が効く。半加法的な列の合計、粒度の異なるファクト同士の直接結合、退行ディメンションでの重複排除漏れ。これらを「禁止事項」として与えると、生成されるSQLの品質が変わる。

**代表的な質問とSQLの対。** いわゆるfew-shotである。業務でよく使われる問いと、その正解SQLを十数件用意するだけで、社内の語彙（「アクティブ顧客」「主力商品」）に対する解釈が安定する。これらはセマンティックレイヤーのメトリクス定義と対応させておく。

そして最も効果的な構成は、**LLMに生テーブルのSQLを書かせないこと**である。セマンティックレイヤーがある環境では、LLMの仕事を「自然言語の問いを、メトリクス名・ディメンション名・期間の組に変換すること」に限定できる。

```json
{
  "metrics": ["net_revenue", "gross_margin_rate"],
  "group_by": ["customer__sales_region", "metric_time__month"],
  "where": "metric_time >= '2026-01-01'",
  "order_by": ["-metric_time__month"],
  "limit": 24
}
```

この構造化されたクエリを、セマンティックレイヤーが検証してSQLへ展開する。存在しないメトリクス名は弾かれ、結合経路は定義どおりに構築され、集約関数は宣言に従う。第1章で述べた「エラーにならない誤り」の多くが、ここで実行前の検証エラーに変わる。生成する自由度を下げることが、信頼性を上げる。

限界もある。定義されていない指標は答えられない。「先月の関東地方における、キャンペーン適用商品の返品率を、初回購入顧客に限って」といった問いに答えるには、その指標と切り口が事前に定義されていなければならない。セマンティックレイヤーは万能の自然言語インターフェースではなく、定義済みの語彙の上でのみ正確に動く仕組みである。この性質を理解したうえで、カバレッジを広げる運用を組む。よく聞かれるのに定義がない指標を検出し、カタログへ追加していくループを回すことになる。

## 構造化されたものと、されていないもの

本章までで、数値と区分値からなる構造化データを、人とAIの両方が正しく読める形に整えてきた。しかし、企業の中にある情報の大半は、この形をしていない。契約書、議事録、問い合わせの本文、設計図、検査写真。第1章で触れた「備考欄に書かれた業務上の重要事実」も同じ系統の問題である。

次章では、これら非構造化データを、ここまで作ってきた構造化モデルへどう接続するかを扱う。

::: tip この章のポイント
- 指標の定義はBIツールの中ではなく、バージョン管理されたコードとして持つ
- Single Source of Truthは単一のテーブルではなく、単一の定義によって作られる
- メトリクスカタログには所有者を明記する。承認者が不在の定義は必ず分裂する
- Text-to-SQLの精度は、列の意味・取りうる値・結合経路・禁止事項という注釈で大きく変わる
- LLMには生SQLではなく、メトリクス名とディメンション名の組を生成させる。自由度を下げることが信頼性を上げる
- セマンティックレイヤーは定義済みの語彙の上でしか正確に動かない。カバレッジを広げる運用が要る
:::
