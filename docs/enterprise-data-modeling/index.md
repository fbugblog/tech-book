# エンタープライズ・データモデリング大全

## 基幹データからAI・LLM基盤への構造化技術

顧客先に入って最初に見るのは、たいてい壊れたデータである。二十年動き続けている基幹システム、部門ごとに分岐したマスタ、誰も仕様を説明できないフラグ列、そして月末に手作業で結合されるCSV。本書は、そうした現実のデータを、分析にもAI/RAGにも耐える構造へ作り替えるための技術書である。

書き手として想定しているのは、大規模エンタープライズの現場に入るデータアーキテクトやFDE（Forward Deployed Engineer）の視点だ。理想的なスキーマを机上で描く話ではなく、動いているシステムを止めずに、履歴を失わずに、業務の言葉を保ったままモデルを移行していく話をする。

## 対象読者

- データ基盤の設計・実装を担うデータエンジニア。DWH/レイクハウスのテーブル設計に責任を持つ人
- 顧客のデータ活用を支援するITコンサルタント。業務要件をスキーマに翻訳する立場の人
- RAGやText-to-SQLを業務データの上に載せようとしているAIエンジニア。検索精度がモデルではなくデータ構造で決まる場面に直面している人

SQLの読み書きと、スタースキーマという語の意味は前提にする。一方で、特定のクラウドDWH製品の知識は要求しない。

## 本書の構成

| 章 | 扱うこと |
| --- | --- |
| 第1章 | モデリングの前提がAI/LLMによってどう変わったのかを捉え直す |
| 第2章 | Kimball手法。分析クエリに最適化されたディメンショナルモデルを厳密に設計する |
| 第3章 | Data Vault 2.0。変更と監査に耐える統合層をどう組むか |
| 第4章 | セマンティックレイヤー。ビジネスの定義をコードとして一元管理する |
| 第5章 | 非構造化データ、ナレッジグラフ、GraphRAGを見据えたモデリング |

第2章と第3章は競合する手法ではない。統合層をData Vaultで受け、配信層をKimballで出す構成は実務でよく採る形であり、第4章のセマンティックレイヤーはその上に乗る。第5章は、そこまでに整えた構造化データへ非構造化データを接続する話になる。

## コードについて

- SQLは断りのない限りPostgreSQL 16の方言で書く。Snowflake・BigQuery・Databricksでは関数名や型名が変わるが、設計の意図はそのまま読み替えられる
- セマンティックレイヤーの例はdbt（MetricFlow）系のYAMLを想定して書く
- グラフのクエリはopenCypher系の記法で書く
- 掲載するDDLは設計意図を示すための抜粋であり、インデックスや権限設定は省いている
