# 第5章 AI・RAG・ナレッジグラフを見据えた高度データモデリング

「先月、A社との取引で遅延が出た案件について、契約上のペナルティ条項と、過去の同種案件での対応を教えてほしい」。

この問いは、実務ではごく普通のものだ。しかし、これに答えるには二種類のデータを横断する必要がある。遅延の事実と金額は基幹システムの中にあり、ペナルティ条項は契約書PDFの中にあり、過去の対応は議事録とメールの中にある。前章までに整えたのは前者だけである。本章では、後者をどう接続するかを扱う。

## 非構造化データは、単体では検索できない

RAGの初期の実装は、文書をチャンクに割り、ベクトル化し、類似度で引く、という手順だった。この構成が業務データで失敗する理由は明快である。業務上の問いは、ほぼ必ず構造化された条件を含むからだ。「先月の」「A社との」「未完了の」といった条件は、意味的類似度では表現できない。「A社」と「B社」のベクトルは近く、「先月」と「昨年」のベクトルも近い。近いものを引いてくる仕組みは、厳密な条件で絞る用途には向かない。

したがって、設計の出発点は次のようになる。**非構造化データは、構造化データのキーを持たなければならない。** 文書は宙に浮いた文字列ではなく、特定の顧客、特定の契約、特定の案件に紐づく成果物である。その紐づけをチャンクのメタデータとして持たせる。

```sql
create table doc_chunk (
  chunk_id        bigint generated always as identity primary key,
  document_id     bigint      not null references document(document_id),
  chunk_index     int         not null,          -- 文書内の順序
  content         text        not null,
  embedding       vector(1024),                  -- pgvector

  -- ここからが構造化モデルへの接続点
  customer_hk     bytea       references hub_customer(customer_hk),
  contract_id     varchar(32),
  document_type   varchar(32) not null,          -- contract / minutes / ticket
  effective_from  date,                          -- 文書の有効期間
  effective_to    date,
  confidentiality varchar(16) not null,          -- 権限フィルタ用
  source_uri      text        not null,          -- 原本の所在（出典表示に使う）
  page_no         int,
  ingested_at     timestamptz not null
);

create index ix_doc_chunk_filter
  on doc_chunk (customer_hk, document_type, effective_to);
```

この設計にしておくと、検索は「メタデータで絞ってからベクトル検索する」という自然な形になる。

```sql
select c.content, c.source_uri, c.page_no,
       c.embedding <=> :query_embedding as distance
  from doc_chunk c
 where c.customer_hk = :customer_hk               -- 構造化データ側で特定した顧客
   and c.document_type = 'contract'
   and (c.effective_to is null or c.effective_to >= current_date)
   and c.confidentiality = any(:allowed_levels)   -- 権限は検索の前段で効かせる
 order by distance
 limit 20;
```

権限のフィルタを検索の中に置いている点に注意してほしい。取得後のフィルタリングでは、上位20件がすべて権限外だった場合に何も返らない。また、そもそも見えてはいけない文書がモデルのコンテキストに入る経路を作るべきではない。行レベルセキュリティは、RAGにおいても検索条件の一部として設計する。

`source_uri` と `page_no` も必須である。生成された回答の根拠を原本まで遡れないRAGは、業務では採用されない。出典表示は機能ではなく、モデルの設計要件だと考えたほうがよい。

## 紐づけをどう作るか——エンティティ解決

<!-- textlint-disable ja-technical-writing/ja-unnatural-alphabet -->

問題は、この `customer_hk` をどう埋めるかである。契約書PDFのどこにも顧客番号は書かれていない。書かれているのは「株式会社ＡＢＣ商事」という表記だけだ。第1章で挙げたマスタ重複の問題が、ここで再び現れる。

<!-- textlint-enable ja-technical-writing/ja-unnatural-alphabet -->

現実的な手順は次のようになる。

1. **抽出**：文書から候補となる固有表現を取り出す。LLMで抽出し、構造化出力として受け取る
2. **正規化**：法人格表記、全角半角、旧字体、空白を規約に沿って揃える
3. **候補検索**：Hubのビジネスキー一覧に対し、正規化済み文字列で曖昧検索する
4. **判定**：スコアが閾値を超えたものを紐づけ、超えないものは保留にする
5. **記録**：判定の根拠と信頼度を残す

```sql
create table doc_entity_link (
  document_id   bigint      not null references document(document_id),
  entity_type   varchar(32) not null,       -- customer / product / contract
  entity_hk     bytea       not null,       -- Hub のハッシュキー
  mention_text  text        not null,       -- 文書中の表記そのまま
  match_method  varchar(64) not null,       -- 'exact' / 'fuzzy_v2' / 'llm_v3' / 'human'
  confidence    numeric(5,4) not null,
  reviewed_by   varchar(64),                -- 人手確認した場合の担当
  linked_at     timestamptz not null,
  primary key (document_id, entity_type, entity_hk)
);
```

第3章のSame-As Linkと同じ思想である。紐づけは推定であり、推定は必ず間違える。だから、判定の方法と信頼度をデータとして持ち、後から見直せるようにする。信頼度が低い紐づけは検索対象から外す、あるいは回答時に「推定による関連付け」と明示する、といった運用が可能になる。

紐づけを完全自動にしようとしないことも重要だ。件数の少ない重要な契約は人手で確認し、`match_method = 'human'` として記録する。すべてを自動化するより、重要度で分けるほうが早く価値が出る。

## ナレッジグラフとベクトルの役割分担

エンティティの紐づけができると、次の形が見えてくる。文書のチャンクと、業務上のエンティティと、エンティティ同士の関係が、一つのネットワークを作る。これがナレッジグラフである。

グラフの基本構成要素は三つだ。

- **ノード（Entity）**：顧客、契約、案件、商品、担当者、文書
- **エッジ（Relationship）**：締結した、参照する、後継である、担当する
- **プロパティ（Attribute）**：ノードやエッジに付く属性。金額、期間、信頼度

ここで、ベクトル検索とグラフ検索の役割分担をはっきりさせておく。

| | ベクトル検索 | グラフ検索 |
| --- | --- | --- |
| 得意なこと | 言い換えを含む意味的な近さの発見 | 明示された関係の正確な追跡 |
| 苦手なこと | 厳密な条件指定、多段の関係 | 表現のゆれ、未定義の関係 |
| 典型的な問い | 類似の条項はどれか | この契約の改定元はどれか |
| 誤りの出方 | 関係ないものが混ざる | 関係が未登録なら何も返らない |

両者は補完関係にある。実務で有効なのは、**グラフで対象を絞り、ベクトルで内容を引く**という組み合わせだ。冒頭の問いに戻ると、処理はこう分解される。

1. 構造化データ（ファクト）から、先月のA社との遅延案件を特定する
2. グラフをたどり、その案件に紐づく契約と、その改定元の契約をすべて集める
3. その契約群のチャンクに限定して、「遅延」「違約金」に意味的に近い箇所をベクトル検索する
4. 同じ商品カテゴリで過去に遅延が発生した案件をグラフでたどり、その議事録を同様に検索する
5. 集めた根拠と、ファクトから取った数値を添えて回答を生成する

ベクトル検索だけでは2と4ができない。グラフだけでは3ができない。そしてどちらも、1の数値を正確には出せない。三つの層が揃って初めて、業務で使える回答になる。

## GraphRAGを見据えたグラフモデリング

Microsoftが2024年に公開したGraphRAGをはじめ、グラフ構造を用いたRAGの手法が実用段階に入っている。素朴なベクトルRAGが苦手とする「全体を俯瞰する問い」——「この顧客との関係で繰り返し起きている問題は何か」——に答えるには、個々のチャンクではなく、エンティティ間の関係とその要約が要るからだ。

グラフを設計するときの実務的な指針を挙げる。

**ノードの粒度は、業務のエンティティに合わせる。** 文書をノードにするか、文書から抽出した概念をノードにするかで設計が分かれるが、既存の構造化モデルがあるなら、そのHubの粒度に合わせるのが最も保守しやすい。基幹データとグラフのエンティティが一対一で対応していれば、両者の同期が単純なジョブになる。抽出した概念を勝手にノード化すると、同義語が増殖して手に負えなくなる。

**エッジには必ず出所と時制を持たせる。** 「A社がB社を買収した」という関係には、いつの情報か、どの文書から抽出したか、どの程度確かかが伴う。これらをプロパティとして持たないグラフは、更新できなくなる。

```cypher
MERGE (a:Customer {hk: $acquirer_hk})
MERGE (b:Customer {hk: $target_hk})
MERGE (a)-[r:ACQUIRED]->(b)
  ON CREATE SET r.valid_from = date($valid_from),
                r.source_document_id = $document_id,
                r.extraction_method = 'llm_v3',
                r.confidence = $confidence,
                r.created_at = datetime()
```

**関係の種類は絞る。** 抽出器に自由に関係名を作らせると、`SUPPLIES` `PROVIDES` `DELIVERS_TO` が混在し、クエリが書けなくなる。許容する関係型をあらかじめ列挙し、抽出時に分類問題として解かせる。分類できないものは `RELATED_TO` に落として、元の表現をプロパティに残す。オントロジーを先に決めるということであり、これはモデリングの仕事である。

**コミュニティ要約を持つ。** GraphRAG系の手法の核心は、グラフを密に結合した部分集合（コミュニティ）に分割し、それぞれの要約をあらかじめ生成しておく点にある。俯瞰的な問いには、個々のチャンクではなく、この要約を返す。要約もまたデータであり、いつ・どのバージョンのグラフから生成されたかを記録して、再生成の対象として管理する。

```sql
create table graph_community_summary (
  community_id    varchar(64) primary key,
  level           int         not null,     -- 階層の深さ
  member_count    int         not null,
  summary         text        not null,
  embedding       vector(1024),
  graph_version   varchar(32) not null,     -- どの時点のグラフから生成したか
  generated_at    timestamptz not null
);
```

**グラフDBを必ず導入する必要はない。** ノード数が数百万程度までなら、リレーショナルDBの隣接リストと再帰CTEで十分に動く。第1章の表で述べたとおり、グラフモデルの価値は多段の関係探索にあり、それが本当に必要かを見極めてから専用DBを検討すればよい。「グラフっぽいから」でNeo4jを入れて運用チームが疲弊する構成は、現場でよく見る失敗である。

## 三層をつなぐ

ここまでで、本書が扱ってきた層が揃った。

```text
       [ セマンティックレイヤー ]  … 指標と語彙の定義（第4章）
                  │
    ┌─────────────┼─────────────┐
    │             │             │
[ ファクト ]  [ ナレッジグラフ ]  [ ベクトル索引 ]
 数値と集計      関係の追跡        意味的な検索
    │             │             │
    └─────────────┴─────────────┘
                  │
       [ Data Vault / Raw 層 ]    … 出所と履歴（第3章）
```

三つの層は、共通のエンティティキーで結ばれている。ファクトの `customer_key`、グラフの `Customer` ノード、チャンクの `customer_hk` が同じ顧客を指しているという保証があって初めて、横断した問いに答えられる。この保証を作ることが、Hubを置き、名寄せを明示的なデータとして持ち、紐づけの信頼度を記録してきた理由である。

本書の主張は、結局のところ一つに収束する。AI時代のデータモデリングとは、**意味を、人の頭の中からデータの中へ移す作業**である。列の意味、指標の定義、エンティティの同一性、文書と業務の対応関係。これらはこれまで、現場の熟練者が暗黙に補ってきた。その補完をあてにできない読み手が増えた以上、補完されていた部分を明示的な構造として書き下すしかない。

その作業は地味で、業務へのヒアリングを伴い、自動化しきれない。だが、ここを飛ばして上物だけを作ったシステムは、デモでは動き、本番では信用されない。顧客の現場でデータに向き合う者の仕事は、いまもその地味な作業の側にある。

::: tip この章のポイント
- 非構造化データは、構造化モデルのキーをメタデータとして持たせて初めて業務で使える
- 権限フィルタと出典（URI・ページ）は、後付けの機能ではなく検索設計の一部である
- 文書とエンティティの紐づけは推定である。方法・信頼度・確認者をデータとして残す
- ベクトルは意味的な近さ、グラフは明示された関係。グラフで絞ってベクトルで引く組み合わせが効く
- グラフの関係型は事前に列挙する。抽出器に自由に作らせると、クエリが書けなくなる
- ファクト・グラフ・ベクトルの三層は、共通のエンティティキーで結ばれていなければ横断できない
:::
