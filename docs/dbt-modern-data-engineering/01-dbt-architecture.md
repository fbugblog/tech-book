# 第1章 dbtの思想とアーキテクチャ——ELTの「T」をコードに引き取る

データ基盤の現場に入ると、ほぼ必ず同じ光景に出会う。データウェアハウスの中に、誰が作ったのか分からないビューが積み上がっているのだ。`sales_summary_v2`、`sales_summary_v2_fix`、`sales_summary_final`。どれが正しいのかを知っている人は、たいてい半年前に退職している。

この状態は、担当者の怠慢から生まれたものではない。SQLという言語には、コードを整理するための仕組みが決定的に欠けていたからである。関数もなければ、モジュールの分割もなく、依存関係を宣言する方法もない。テストを書く文化も育たなかった。その結果、変換ロジックはウェアハウスの中に手作業で置かれた成果物として堆積し、誰も全体像を把握できなくなる。

dbtがやったのは、この構造的な欠落を埋めることだった。本章では、dbtがELTのどこに座り、具体的に何を肩代わりしているのかを押さえる。

## ETLからELTへ——「T」が倉庫の中に移った

かつてのデータ基盤では、変換処理（Transform）はウェアハウスの外で行われていた。専用のETLサーバーが源泉システムからデータを引き抜き（Extract）、サーバーのメモリ上で加工し（Transform）、整形済みのデータだけをウェアハウスに書き込む（Load）。ウェアハウスのストレージも計算資源も高価だったので、汚いデータを入れる余裕がなかったのである。

この前提を崩したのが、クラウドデータウェアハウスの登場だった。SnowflakeやBigQueryは、ストレージを安価に、計算資源を弾力的に提供する。生データをそのまま放り込んでおくコストが、変換してから入れる手間より安くなった。こうして順序が入れ替わる。まず生のまま入れ（Extract-Load）、変換はウェアハウスの中でSQLとして実行する（Transform）。これがELTである。

ELTへの移行は、単なる順序の入れ替えにとどまらない副作用をもたらした。変換ロジックの置き場所が、専用ツールのGUIからSQLへ移ったのである。SQLはテキストであり、テキストはGitで管理できる。ここに、ソフトウェアエンジニアリングの作法を持ち込む隙間が生まれた。

> ELTの本質は、変換処理がテキストファイルになったことにある。テキストになった瞬間、レビューもテストもバージョン管理も適用できる。

dbtは、この隙間にぴたりとはまるツールとして設計されている。データを動かす機能は持っていない。抽出も転送もしない。dbtがやるのは、ウェアハウスに対して正しい順序でSQLを投げることだけである。

## dbtの正体はSQLコンパイラである

dbtを初めて触る人が戸惑うのは、「dbtは何をしているのか」が見えにくい点だ。答えは単純で、dbtはテンプレート化されたSQLを素のSQLへコンパイルし、ウェアハウスへ発行するツールである。

次のモデル（`models/marts/fct_orders.sql`）を見てほしい。

```sql
select
    o.order_id,
    o.customer_id,
    o.ordered_at,
    sum(i.amount) as order_amount
from {{ ref('stg_shop__orders') }} as o
left join {{ ref('stg_shop__order_items') }} as i
    on o.order_id = i.order_id
group by 1, 2, 3
```

`ref()` の部分がdbt固有の記法である。これは「`stg_shop__orders` という名前の別のモデルを参照する」という宣言であり、dbtはコンパイル時にこれを実際のテーブル名（`analytics.dbt_prod.stg_shop__orders` のような完全修飾名）へ置き換える。さらに、モデルの設定が `table` であれば、全体を `create table as` で包んでウェアハウスへ送る。

ここで重要なのは、`ref()` が二つの仕事を同時にこなしている点だ。

一つは名前解決である。開発環境では自分専用のスキーマを、本番環境では本番スキーマを指すように、同じコードのまま参照先が切り替わる。環境ごとにSQLを書き分ける必要がなくなる。

もう一つが依存関係の宣言である。`fct_orders` が `stg_shop__orders` を `ref()` しているという事実から、dbtは「後者を先に作らなければならない」と判断する。プロジェクト全体の `ref()` を集めれば、モデル同士の依存グラフ（DAG）が自動的に組み上がる。実行順序を人間が管理する必要はない。

```bash
dbt run          # DAGの順序どおりにモデルを構築する
dbt build        # モデル・テスト・シード・スナップショットをまとめて実行する
dbt run -s fct_orders+   # fct_orders とその下流だけを実行する
```

`+` や `@` といったセレクタで、DAGの一部だけを切り出して実行できる点も、依存グラフを持っているからこそ成立する機能である。

## マテリアライゼーション——「どう作るか」を設定に追い出す

SQLで変換を組むとき、いちばん面倒なのは `create table as` や `insert into` といった構築方法の記述である。テーブルにするのかビューにするのか、増分更新にするのかは、要件次第で何度も変わる。そのたびにクエリ本体を書き換えるのは筋が悪い。

dbtはここを設定として切り出した。モデルのSQLには `select` 文だけを書き、構築方法はマテリアライゼーションとして宣言する。

```sql
{{ config(materialized='incremental', unique_key='order_id') }}

select * from {{ ref('stg_shop__orders') }}

{% if is_incremental() %}
where ordered_at > (select max(ordered_at) from {{ this }})
{% endif %}
```

主なマテリアライゼーションは四つある。`view` はビューを作るだけで保存コストがかからず、`table` は毎回作り直すため単純で壊れにくい。`incremental` は差分だけを追記・更新するため大規模テーブル向きで、`ephemeral` は実体を作らずCTEとして下流に埋め込まれる。

選択の指針ははっきりしている。まず全部 `table` か `view` で作り、実行時間かコストが問題になって初めて `incremental` に切り替える。増分モデルは、途中でロジックを変えたときの再構築や、遅れて到着したデータの扱いといった難しさを持ち込む。必要になる前に導入すると、運用の負債にしかならない。

## ソフトウェアエンジニアリングの作法を持ち込む

dbtが評価されている理由は、SQLの実行順序を解決したからではない。SQLの世界に、ソフトウェア開発が数十年かけて育ててきた作法を持ち込んだからである。

**バージョン管理**が最も分かりやすい。モデルは `.sql` ファイル、設定は `.yml` ファイルであり、すべてGitリポジトリに入る。「なぜこの売上の定義はこうなっているのか」という問いに、`git log` と Pull Request のコメントで答えられる。ウェアハウスの中のビューに対しては、この問いに答える手段がなかった。

**DRY原則**は `ref()` とマクロで実現する。「有効な注文とは何か」という定義を一つのモデルに閉じ込め、下流はそれを `ref()` する。定義が変わったときに直す場所は一か所になる。同じロジックをコピーした五つのクエリを探し回る作業から解放される。

**モジュール化**は、一つのモデルを一つの責務に絞ることで達成する。500行の巨大なクエリを、20行のモデル10個に割り、`ref()` でつなぐ。個々のモデルは読めるし、テストも書けるし、中間結果を `select` して確かめられる。

**テスト**については第4章で詳しく扱うが、`unique` や `not_null` といった制約をYAMLに書くだけで、それがSQLのアサーションへコンパイルされる。データに対するユニットテストが、設定ファイルの数行で書ける。

**ドキュメント**も同様で、YAMLに書いた説明文とDAGから、検索可能なドキュメントサイトが生成される。「このカラムは何か」をSlackで聞いて回る時間が減る。

これらはどれも、ソフトウェア開発では当たり前の道具立てである。dbtの発明は、それをSQLの世界に持ち込む具体的な形を示した点にある。

## dbt Core と dbt Cloud——どちらを選ぶか

dbtには二つの提供形態がある。判断を誤ると後から動きにくくなるので、違いを押さえておきたい。

**dbt Core** はApache 2.0ライセンスのオープンソースCLIである。`pip install` で入り、手元でもCIサーバーでも動く。dbtの機能そのものはここにすべて含まれている。ただし、スケジューリングも、実行ログの保管も、ドキュメントのホスティングも自前で用意する必要がある。

**dbt Cloud** は、Coreの実行環境にスケジューラー、Web IDE、ドキュメントホスティング、CI連携、権限管理などを載せたマネージドサービスである。特にSlim CI（第5章で扱う）の設定と、本番実行のメタデータ管理は、自前で組むと手間のかかる部分をよく吸収している。

選定の軸は次のように整理できる。すでにAirflowやDagsterを運用していて、dbtをその中の一ジョブとして走らせるなら、Coreで十分である。オーケストレーターを持っておらず、データチームが少人数で、SQLは書けるがインフラ運用に人を割けないなら、Cloudのほうが総保有コストは下がりやすい。

なお、dbt Labsは2025年にRust実装の新しい実行エンジン「Fusion」を発表しており、パース速度や静的解析の面で従来のPython実装から大きく変わる方向にある。移行を前提とした設計判断は時期尚早だが、大規模プロジェクトの立ち上げ時には最新の状況を確認しておくとよい。

## ローカル開発環境を組む

最後に、手元で書き始めるまでの最短経路を示す。

```bash
# 仮想環境を作り、アダプターと一緒に入れる
python -m venv .venv
source .venv/bin/activate
pip install dbt-core dbt-snowflake   # アダプターは使うウェアハウスに合わせる

# プロジェクトの雛形を作る
dbt init my_analytics
cd my_analytics

# 接続確認
dbt debug
```

接続情報は `~/.dbt/profiles.yml` に書く。ここには認証情報が入るので、リポジトリには絶対に置かない。環境変数から読む形にしておくと、CIでもそのまま使える。

```yaml
my_analytics:
  target: dev
  outputs:
    dev:
      type: snowflake
      account: "{{ env_var('DBT_SNOWFLAKE_ACCOUNT') }}"
      user: "{{ env_var('DBT_SNOWFLAKE_USER') }}"
      password: "{{ env_var('DBT_SNOWFLAKE_PASSWORD') }}"
      role: TRANSFORMER
      warehouse: TRANSFORMING
      database: ANALYTICS
      schema: "dbt_{{ env_var('USER') }}"
      threads: 8
```

`schema` を開発者ごとに分けている点に注目してほしい。これで各自が自分専用のスキーマにモデルを作り、本番を壊さずに試せる。dbtの開発体験の良さは、この「安全に壊せる場所」があることに支えられている。

エディターはVS CodeかCursorに、dbt Power Userのような拡張を入れる構成が定番である。`ref()` からのジャンプ、コンパイル結果のプレビュー、モデル単体の実行がエディターから行えるようになり、ターミナルとの往復が減る。

`threads` は同時実行数であり、DAG上で並列に走らせられるモデルの数を決める。開発環境では4〜8程度、本番ではウェアハウスのサイズに合わせて調整する。ここを上げすぎるとウェアハウス側が詰まるので、実行時間を見ながら決める。

::: tip この章のポイント
- クラウドウェアハウスの登場でETLはELTになり、変換ロジックがテキスト（SQL）としてGit管理できるようになった。dbtはその隙間に座るツールである
- dbtの正体はSQLコンパイラであり、`ref()` が名前解決と依存関係の宣言という二つの仕事を同時にこなす。実行順序は依存グラフから自動で決まる
- 「何を作るか」はSQLに、「どう作るか」はマテリアライゼーションの設定に分離する。増分モデルは必要になってから導入する
- dbtの価値は、バージョン管理・DRY・モジュール化・テスト・ドキュメントという既存の作法をSQLの世界に持ち込んだことにある
- CoreとCloudの選定軸は、オーケストレーターをすでに持っているかどうかと、インフラ運用に人を割けるかどうかである
:::
