# 第5章 CI/CD・オーケストレーション・本番運用——壊れたまま本番に入らせない

ここまでの四章で、モデルを層に分け、共通処理をまとめ、テストを積んできた。残るのは、それを毎日確実に回す仕組みである。

この章で扱う三つは、どれも「人間が忘れる」ことへの対策だと考えると筋が通る。ドキュメントは、書いた本人が半年後に忘れるから自動生成する。CIは、レビュアーが影響範囲を見落とすから機械に確かめさせる。オーケストレーションは、深夜のジョブ失敗に人間が気づけないから、リトライと通知を仕組みに埋める。

## dbt docsとリネージ——「この数字はどこから来たのか」に答える

データ基盤の運用で最も頻繁に来る問い合わせは、障害報告ではない。「この数字はどうやって計算されているのか」である。

dbtは、この問いに答えるためのドキュメントサイトを、プロジェクトの構造から生成する。

```bash
dbt docs generate   # メタデータとカタログを集める
dbt docs serve      # ローカルでブラウザーに表示する
```

`dbt docs generate` は二つの成果物を作る。`manifest.json` はモデル・テスト・依存関係・説明文といったプロジェクトの全体像を持ち、`catalog.json` はウェアハウスに実際に存在するテーブルの列構成や行数といった実体情報を持つ。前者はプロジェクトのコードから、後者はウェアハウスへの問い合わせから作られる。

生成されるサイトの中心が**リネージグラフ**である。あるモデルを選ぶと、それが源泉からどう作られ、下流の何に使われているかが図で表示される。この画面が効くのは、次の三つの場面だ。

**影響調査**では、「このカラムを消したら何が壊れるか」を数秒で答えられる。従来は全リポジトリを検索して回る作業だった。

**障害の原因追跡**では、下流のマートが壊れたとき、上流をさかのぼって原因の層を特定できる。

**引き継ぎ**では、新しく入った人がプロジェクトの構造を掴む入口になる。口頭の説明より速い。

ただし、リネージグラフの価値は説明文の充実度に比例する。`description` が空のモデルが並ぶドキュメントは、箱の絵が並んでいるだけで役に立たない。

説明を書く負担を減らすため、**docsブロック**という仕組みがある。長い説明や、複数のモデルで共有する定義に使う。

```markdown
<!-- models/marts/finance/_finance__docs.md -->
{% docs order_amount %}
注文金額。日本円、税込。

- クーポン適用後の金額である
- 送料は含まない
- キャンセル済みの注文はこのテーブルに含まれないため、常に正の値をとる
{% enddocs %}
```

```yaml
columns:
  - name: order_amount
    description: '{{ doc("order_amount") }}'
```

同じカラムが複数のマートに現れる場合、定義を一か所に置ける。定義がずれる事故を防ぐという意味では、第3章のDRY原則をドキュメントに適用したものと言える。

説明を書く優先順位も決めておきたい。**マートは全カラムに書く**。外部に公開する契約なのだから、説明のないカラムは契約違反である。Staging層は、源泉の列名から自明でないものだけでよい。すべてに書こうとすると、`order_id は注文ID` のような無内容な説明で埋まる。

生成したサイトの公開先は、dbt Cloudならホスティング機能がそのまま使える。dbt Coreの場合は、`target/` 配下の静的ファイルをS3やGitHub Pagesに置く構成が一般的である。

## Slim CI——差分だけをテストする

Pull Requestのたびにプロジェクト全体を実行していては、CIは使いものにならない。モデルが500個あれば、一回の実行に数十分とそれなりの請求が発生する。レビューのたびにそれを払うのは現実的ではない。

かといって、テストを省略すれば壊れたモデルがマージされる。この矛盾を解くのが**Slim CI**である。

考え方はこうだ。dbtは本番実行時に `manifest.json` を残している。これは本番のプロジェクトがどういう状態だったかの記録である。CIで、この本番の `manifest.json` と、いま手元にあるコードを比較すれば、**変更されたモデルが特定できる**。

```bash
# 変更されたモデルとその下流だけを構築・テストする
dbt build --select state:modified+ --defer --state ./prod-artifacts
```

三つのオプションが組み合わさっている。

`state:modified+` は「本番と比べて変更されたモデル」と、その `+` で示される下流を選ぶ。変更していないモデルは実行対象から外れる。

`--state ./prod-artifacts` は、比較対象となる本番の `manifest.json` の置き場所を指す。

`--defer` が肝心な部分である。変更対象の上流モデルは、CI環境で作り直すのではなく**本番のテーブルを参照する**。これがないと、下流だけを実行しても上流のテーブルがCI環境に存在せず失敗する。

この三つで、実行対象は「変更したモデルと、その影響を受ける下流」に絞られる。数十分の実行が、数分で終わる。

GitHub Actionsでの実装例を示す。

```yaml
# .github/workflows/dbt-ci.yml
name: dbt CI

on:
  pull_request:
    paths: ['models/**', 'macros/**', 'tests/**', 'seeds/**', 'dbt_project.yml']

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      DBT_SNOWFLAKE_ACCOUNT: ${{ secrets.DBT_SNOWFLAKE_ACCOUNT }}
      DBT_SNOWFLAKE_USER: ${{ secrets.DBT_SNOWFLAKE_USER }}
      DBT_SNOWFLAKE_PASSWORD: ${{ secrets.DBT_SNOWFLAKE_PASSWORD }}
      # PRごとに専用スキーマを使い、実行の衝突を避ける
      DBT_CI_SCHEMA: ci_pr_${{ github.event.pull_request.number }}

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - run: pip install -r requirements.txt

      - run: dbt deps

      # 本番実行が残した manifest.json を取ってくる
      - name: 本番のアーティファクトを取得
        run: |
          mkdir -p prod-artifacts
          aws s3 cp s3://my-dbt-artifacts/prod/manifest.json prod-artifacts/

      - name: 差分のみビルドとテスト
        run: dbt build --select state:modified+ --defer --state ./prod-artifacts

      - name: CIスキーマを片付ける
        if: always()
        run: dbt run-operation drop_ci_schema --args "{schema: $DBT_CI_SCHEMA}"
```

実装上の注意点を三つ挙げる。

**PRごとにスキーマを分ける**。複数のPRが同時に走ると、同じスキーマに書き込んで互いを壊す。PR番号をスキーマ名に入れて分離し、最後に片付ける。片付けを `if: always()` にしておかないと、失敗時にスキーマが残り続ける。

**本番アーティファクトの鮮度に注意する**。`manifest.json` が古いと、差分判定がずれる。本番ジョブの成功時に必ず最新版をアップロードする運用にしておく。

**`state:modified` はSQLの変更を見ている**。マクロを変更した場合、それを使うモデルは「変更された」と判定されないケースがある。マクロやパッケージを触るPRでは、選択範囲を広げるか全体実行に切り替える判断が要る。

Slim CIに加えて、**SQLの静的チェック**も入れておくと効果が高い。SQLFluffのようなリンターをCIに組み込めば、スタイルの指摘をレビューから追い出せる。

```bash
sqlfluff lint models/ --dialect snowflake
```

人間のレビューは、ロジックとモデル設計に集中させたい。インデントとキーワードの大文字小文字は機械に任せる。

## デプロイを分ける

CIが通ったコードを本番へ反映する流れも決めておく。実務で扱いやすいのは、環境を三つに分ける構成である。

**開発環境**は各開発者のスキーマ（`dbt_alice` など）で、手元から実行する。壊しても誰も困らない場所だ。

**CI環境**はPRごとの一時スキーマで、マージ前の検証にだけ使い、実行後に消す。

**本番環境**は `main` へのマージをきっかけにデプロイされ、スケジュール実行が走る。

本番デプロイでは、初回だけ全体を構築し、以降は増分にしたい場面がある。`state:modified` は本番でも使える。

```bash
dbt build --select state:modified+ --state ./prod-artifacts --target prod
```

ただし、本番で差分だけを反映する運用は、アーティファクトの管理を誤ると不整合を生む。デプロイは全体実行、日次のスケジュールは必要なモデルだけ、という切り分けのほうが事故が少ない。

## オーケストレーション——dbtは単独では回らない

dbt自体にスケジューラーはない。dbt Cloudを使うならジョブ機能がそれを担うが、dbt Coreの場合は外部のオーケストレーターが要る。

そもそも、実運用のパイプラインはdbtだけで完結しない。源泉からの取り込み、dbtによる変換、BIのキャッシュ更新や機械学習の再学習といった後続処理が連なる。dbtはその中の一工程である。

主要な選択肢を三つ挙げ、性格の違いを整理する。

**Airflow** は最も広く使われているワークフローエンジンである。dbtと組み合わせる場合、単に `dbt build` を一つのタスクとして叩く方法もあるが、それではdbtのモデル単位の失敗がAirflowから見えない。`astronomer-cosmos` を使うと、dbtプロジェクトのDAGをAirflowのタスクグループとして展開でき、モデル単位のリトライと可視化が得られる。

```python
from cosmos import DbtTaskGroup, ProjectConfig, ProfileConfig
from airflow.decorators import dag
import pendulum

@dag(schedule="0 5 * * *", start_date=pendulum.datetime(2026, 1, 1), catchup=False)
def analytics_pipeline():
    transform = DbtTaskGroup(
        project_config=ProjectConfig("/opt/airflow/dbt/my_analytics"),
        profile_config=ProfileConfig(
            profile_name="my_analytics",
            target_name="prod",
            profiles_yml_filepath="/opt/airflow/dbt/profiles.yml",
        ),
    )
    transform

analytics_pipeline()
```

**Dagster** は、タスクではなく**資産（アセット）**を中心に据えた設計を持つ。「このテーブルを最新にする」という宣言が単位になるため、dbtのモデルという概念と相性がよい。`dagster-dbt` を使うと、dbtの各モデルがDagsterのアセットとして自動的に登録され、dbt以外のデータ資産と一つのリネージに統合される。dbtを中心にデータ基盤を組むなら、最初から検討する価値がある。

**Prefect** は、Pythonのコードにデコレーターを付けていく軽量な書き味が特徴である。既存のPythonスクリプトが多く、それを段階的にワークフロー化したい場合に導入コストが低い。

選定の目安を書いておく。すでにAirflowが社内で動いていて運用ノウハウがあるなら、無理に変える必要はない。新規に立ち上げ、かつdbtが変換処理の中心にあるなら、Dagsterの資産モデルが素直に効く。Pythonの処理が主役でdbtが一部なら、Prefectが馴染みやすい。

## 障害からの回復を設計する

夜間バッチは必ず落ちる。落ちない前提でパイプラインを組むと、朝の対応が長くなる。

**冪等性**を最初に確認したい。同じジョブを二回実行しても結果が同じになるか、という性質である。`table` マテリアライゼーションは毎回作り直すので冪等だ。`incremental` は、`unique_key` を設定していれば重複更新にならないが、設定を忘れると二重に行が入る。増分モデルを作ったら、二回続けて実行して行数が変わらないことを必ず確認する。

**途中からの再開**も用意しておく。dbtには失敗地点から再実行する機能がある。

```bash
dbt retry
```

直前の実行結果（`target/run_results.json`）を読み、失敗したノードとその下流だけを再実行する。300モデルのうち280個目で落ちたときに、最初からやり直す必要がなくなる。

**早期の打ち切り**も場合によっては有効である。

```bash
dbt build --fail-fast
```

最初の失敗で即座に止める。上流が壊れているときに、無駄な計算を続けてコストを払うのを防ぐ。日次バッチでは `--fail-fast` を付けず、極端に高価なモデル群を含む処理では付ける、といった使い分けになる。

**リトライの設計**では、区別が要る。ネットワークの一時障害やウェアハウスの一時的な過負荷は、自動リトライで回復する。一方、テストの失敗はデータの問題であり、リトライしても結果は変わらない。オーケストレーター側で、モデル構築の失敗は二回まで自動リトライし、テストの失敗は即座に通知する、といった分岐を入れておく。

リトライで隠してはいけない失敗もある。テストが落ちているのに再実行で通ったなら、それはデータが途中で変わったということであり、原因を追うべき事象である。

> 自動リトライは、原因の分かっている一時障害にだけ使う。原因の分からない失敗をリトライで消すと、障害の記録そのものが消える。

## 運用を測る

最後に、回り始めたパイプラインをどう監視するかに触れておく。

`dbt build` が出力する `run_results.json` には、各ノードの実行時間が入っている。これを日次で蓄積すると、実行時間の推移が見える。

```python
import json
from datetime import datetime

with open("target/run_results.json") as f:
    payload = json.load(f)

rows = [
    {
        "run_at": payload["metadata"]["generated_at"],
        "node": r["unique_id"],
        "status": r["status"],
        "seconds": r["execution_time"],
    }
    for r in payload["results"]
]
```

これをウェアハウスに書き戻し、dbtのモデルとして扱えば、**パイプラインの実行履歴そのものをdbtで分析できる**。実行時間が伸び続けているモデルや、失敗の多いモデルが一覧で見えるようになる。

見るべき指標は三つで足りる。**実行時間の推移**は、増分化やクラスタリングの検討時期を教えてくれる。**失敗率**は、どのモデルが不安定かを示す。**データの鮮度**は、第4章の `dbt source freshness` と合わせて、利用者への説明責任を果たす材料になる。

この領域を専門に扱う `elementary` のようなパッケージもあり、実行結果の蓄積と可視化を一通り用意してくれる。自前で組む前に、要件が合うかを確認する価値はある。

## 本書のまとめに代えて

五つの章を通じて扱ってきたのは、結局のところ一つのことである。**SQLをソフトウェアとして扱う**、ということだ。

層に分けるのはモジュール化であり、`ref()` は依存性の宣言である。マクロは関数であり、テストはアサーションであり、Slim CIは変更の影響範囲に絞った検証である。どれもソフトウェア開発では数十年前から当たり前だった作法にすぎない。

dbtが特別なのは、新しい概念を発明したからではない。SQLという、それらの作法を受け入れる器を持たなかった言語に、器を用意したからである。ツールがdbtでなくなる日は来るかもしれないが、この作法自体が不要になることはない。

::: tip この章のポイント
- `dbt docs` はプロジェクトの構造から影響調査・原因追跡・引き継ぎに使えるリネージを生成する。価値は説明文の充実度に比例する
- Slim CIは `state:modified+` と `--defer` と `--state` の三つで、変更されたモデルと下流だけに実行を絞る。PRごとにスキーマを分け、必ず片付ける
- オーケストレーターの選定軸は、既存資産（Airflow）・dbt中心の資産モデル（Dagster）・Python主体（Prefect）である
- 増分モデルは二回連続で実行して冪等性を確認する。`dbt retry` で失敗地点から再開でき、`--fail-fast` は高価な処理で効く
- 自動リトライは原因の分かっている一時障害にだけ使う。テストの失敗をリトライで消すと、障害の記録が消える
- `run_results.json` をウェアハウスに蓄積すれば、パイプラインの実行履歴そのものをdbtで分析できる
:::
