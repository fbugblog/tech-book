# 第5章 LLMOps とオブザーバビリティ

オフラインの評価がどれだけ整っていても、それは自分たちが用意した質問に対する成績にすぎない。本番で実際に飛んでくる質問は、想定より雑で、曖昧で、そして想定していない。

この章では、本番環境の挙動を観測し、その観測結果を評価データセットへ還流させ、危険な出力をその場で止めるところまでを扱う。ここまで組んで、ようやく改善のループが閉じる。

## トレースがないと原因に辿り着けない

LLMアプリケーションの障害報告は、たいてい「変な答えが返ってきた」という形で届く。このときスクリーンショット一枚しか手元にないと、調査は始まらない。どの文書が検索されたのか、どんなプロンプトが組み上がったのか、エージェントがどのツールを呼んだのかが分からないからだ。

必要なのは、一回のリクエストを木構造で記録するトレースである。

```
trace: 質問「有給の繰り越しは何日まで？」        1,840ms / $0.012
├── span: retrieve                              210ms
│   ├── span: embed_query                        40ms
│   └── span: vector_search (top_k=5)           170ms   → doc_id 12, 47, 3, 88, 21
├── span: rerank                                180ms   → doc_id 47, 12, 3
├── span: generate                            1,410ms   in 3,204 tok / out 186 tok
└── span: guardrail_output                       40ms   → pass
```

各スパンには、入力、出力、レイテンシ、トークン数、コスト、モデル名、プロンプトのバージョンを持たせる。これがあれば、先の障害報告に対して、検索の失敗なのか生成の失敗なのかを数分で切り分けられる。

計装はOpenTelemetryに寄せておくとよい。生成AI向けのセマンティック規約の整備が進んでおり、属性名を規約に合わせておけば、可視化ツールを乗り換えても計装コードを書き直さずに済む。トレースIDはアプリケーションのログやAPIのレスポンスヘッダとも共有し、利用者からの問い合わせと突き合わせられるようにしておく。

## トレースツールの選択

代表的な三つを比較する。

| ツール | 提供形態 | 特徴 | 向いている状況 |
| --- | --- | --- | --- |
| LangSmith | SaaS中心（セルフホストは上位プラン） | LangChain/LangGraphとの統合が最も深い。データセット管理とオンライン評価が一体 | LangChainで構築し、運用を早く立ち上げたい |
| Phoenix | オープンソース（Arize） | OpenTelemetryとOpenInferenceに準拠。ノートブックでそのまま動く | 特定フレームワークに縛られたくない。実験段階から使いたい |
| Langfuse | オープンソース（クラウド版あり） | セルフホストが容易。プロンプト管理、コスト集計、スコア付けAPIが揃う | データを自社環境から出せない。金融など規制のある領域 |

選定で最初に効くのは機能差ではなく、データをどこに置けるかである。本番のトレースには利用者の入力がそのまま入る。個人情報や機微情報を外部SaaSに送れない組織では、その一点でセルフホスト可能な選択肢に絞られる。

もう一つの判断軸は、評価との接続である。トレースを眺めるだけの基盤には、あまり価値がない。本番のトレースにスコアを付けられること、スコアの付いたトレースを評価データセットへ書き出せること。この二つができるかどうかを確認する。

## フィードバックを設計する

本番のスコア付けには、大きく三つの経路がある。

**明示的フィードバック。** 回答の下に置く「役に立った／立たなかった」のボタンである。実装は簡単だが、押す人は少ない。押される率は数パーセントというのが一般的な水準で、しかも不満を持った人のほうが押しやすいという偏りがある。それでも、否定的なフィードバックが付いたトレースは改善の宝庫である。必ずトレースIDと紐づけて保存し、定期的に全件読む。

否定のボタンに理由の選択肢を添えると、価値が跳ね上がる。「情報が古い」「質問と関係ない」「答えになっていない」「事実が間違っている」の四択で十分だ。これは第1章の壊れ方の分類にそのまま対応しており、どの指標を見るべきかが直接決まる。

**暗黙的フィードバック。** 利用者の行動から品質を推定する。回答をコピーした、引用元の文書を開いた、といった行動は肯定的な信号である。同じ内容を言い換えて質問し直した、数秒で離脱した、人間のオペレーターへエスカレーションした、といった行動は否定的な信号になる。量が取れるのが利点で、明示的フィードバックの数パーセントとは桁が違う。

**オンライン評価。** 本番トラフィックの一部を抽出し、第2章と第4章の判定器を非同期で走らせる。全件に走らせるとコストがかさむため、数パーセントのサンプリングから始める。重要なのは、この結果をダッシュボードで時系列に置くことだ。オフライン評価は変更の前後を比べるものだが、オンライン評価は何も変更していなくても動く。参照している文書が更新された、利用者層が変わった、モデルが更新された。こうした外的要因による劣化は、オンライン評価でしか捕まらない。

そして、この三つで拾った問題ケースを評価データセットへ戻す。否定的フィードバックが付いた質問、オンライン評価で低スコアだった質問、エスカレーションに至った質問。これらを人手で整え、正解を付けて、ゴールデンデータセットに追加する。データセットが本番の現実に近づくほど、オフライン評価の予測力が上がる。

## ガードレールで実行時に止める

評価は事後の計測である。事後に分かっても手遅れな出力——個人情報の混入、明らかな誤情報の断定、危険な指示への応答——には、実行時の検知とブロックが要る。

配置は二段になる。

```
利用者入力 → [入力ガードレール] → 検索 → 生成 → [出力ガードレール] → 利用者
                    ↓ 検知                              ↓ 検知
              定型文で応答して打ち切り           定型文に差し替え／人間へ回す
```

入力側で見るのは、プロンプトインジェクション、権限外の情報を引き出そうとする問い合わせ、扱う範囲を明らかに外れた話題である。出力側で見るのは、個人情報の混入、禁止表現、根拠のない断定、そして第2章の忠実性が極端に低い回答だ。

実装の選択肢を二つ挙げる。

**NeMo Guardrails。** NVIDIAのオープンソース実装で、Colangという専用言語で対話のフローと制約を記述する。入力レール、出力レール、対話レール、実行レールといった層が定義されており、宣言的にルールを書ける。話題の範囲を限定する用途や、特定の問いに定型文を返す用途に向く。

**Llama Guard。** Metaの安全性分類モデルで、入力と出力を安全か否かに分類し、該当するカテゴリを返す。分類器なので判定が速く、汎用の生成モデルに安全性判定をさせるより安定している。カテゴリ体系を自組織の規程に合わせて調整して使う。

現実には、この二つと軽量な検査を組み合わせる。個人情報の検出は正規表現と固有表現抽出で十分な場合が多く、そこにLLMを使うのはコストとレイテンシの無駄である。安いものから順に並べ、通過したものだけを重い検査に回す。

### ガードレール運用の勘所

**レイテンシ。** 出力ガードレールは、利用者を待たせる時間に直接乗る。ストリーミング出力と併用する場合、生成の完了を待ってから検査すると体験を損なう。重要度の高い検査だけを同期で行い、残りは非同期に回して事後の監視に使う、という割り切りが要る。

**誤検知。** ガードレールは必ず誤検知する。過剰にブロックすれば、まともな質問に定型文しか返らないシステムになる。ブロック率は必ず監視対象に入れ、ブロックした入出力はすべて保存して定期的に読む。ブロックが妥当だったかどうかを人間が判定した記録は、そのまま閾値調整の材料になる。

**ブロックの記録。** 何をブロックしたかは、監査の対象になりうる。特に規制のある業種では、検知時刻、検知した規則、入出力、後続の処理を残す。同時に、そのログ自体が機微情報の塊になるため、保存期間とアクセス権を設計に含める。

## ループを閉じる

ここまでの要素を一つの流れに並べると、こうなる。

1. オフライン評価でリリース前に基準線を確認する（第2章・第3章）
2. トレースで本番の一回一回を記録する
3. フィードバックとオンライン評価でスコアを付ける
4. 低スコアのケースを評価データセットへ還流させる
5. データセットが厚くなった状態で、次の変更を評価する

このループが回り始めると、品質の議論の質が変わる。「体感では良くなった気がする」という会話が、「忠実性が0.86から0.91に上がり、否定的フィードバック率は1.8%から1.1%に下がった」という会話になる。

非決定的なシステムを扱う以上、バグをゼロにはできない。できるのは、壊れ方を観測可能にし、劣化を検知可能にし、改善を測定可能にすることだ。本書が「品質保証」という言葉で指してきたのは、その三つである。

::: tip この章のポイント
- 一回のリクエストを木構造で記録するトレースがないと、障害の原因を検索と生成に切り分けられない
- 計装はOpenTelemetryに寄せると、可視化ツールの乗り換えで計装コードを書き直さずに済む
- トレースツールの選定は機能差より先に、データをどこに置けるかと評価に接続できるかで決まる
- フィードバックは明示・暗黙・オンライン評価の三経路で集め、低スコアのケースを評価データセットへ還流させる
- ガードレールは入力側と出力側に二段で置き、安い検査から順に並べる。誤検知率とブロック内容を必ず監視する
- 目指すのはバグのゼロ化ではなく、壊れ方の観測、劣化の検知、改善の測定を可能にすることである
:::
