# 第4章 LLM-as-a-Judge の高度な設計とバイアス制御

ここまでの章で使ってきた指標は、ほとんどが内部でLLMに判定させている。つまり評価パイプラインの信頼性は、判定器としてのLLMの信頼性に乗っている。

その判定器には、人間の評価者とは違う種類の偏りがある。この章では、評価者としてのLLMをどう設計し、既知のバイアスをどう抑えるかを扱う。

## 三つの設計パターン

判定のさせ方は大きく三つに分かれる。

| パターン | やり方 | 向いている場面 | 弱点 |
| --- | --- | --- | --- |
| 絶対評価 | 1件を基準に照らして採点する | 回帰テスト、閾値判定 | スコアが中央に寄りやすい |
| 参照付き評価 | 正解を与えたうえで採点する | 正解が定義できるタスク | 正解の作成コストがかかる |
| 対比評価 | 二つの出力を並べて優劣を選ばせる | モデルやプロンプトの比較 | 位置バイアスが出る。絶対水準が分からない |

CIに組み込む日々の回帰テストには絶対評価が向く。閾値と比較できる数字が必要だからだ。一方、プロンプトAとBのどちらを採用するかという意思決定には、対比評価のほうが判定が安定する。人間でも、答案に点数を付けるより二つを見比べるほうが判断が楽である。

絶対評価を使うときは、スコアを連続値にせず離散ラベルにする。1から5の整数とし、各点に何を意味するかを書き下す。「3点: 主要な情報は正しいが、補足情報に根拠のない記述が一つある」といった具合である。この定義がないと、判定器は毎回違う基準で3と4を分ける。

## G-Evalという型

第3章で使ったG-Evalは、この絶対評価を安定させるための具体的な型として読める。評価基準から評価手順を生成し、手順に沿って採点させる。加えて、元の手法では出力トークンの確率でスコアを加重平均し、整数値に張り付きがちな採点を滑らかにしている。

実装のうえで大事なのは、手順を固定するという発想のほうである。同じ基準文でも、思考手順が毎回違えば結果は揺れる。手順を書き下し、プロンプトの一部として固定し、変更したらバージョンを上げる。評価プロンプトはアプリケーションのプロンプトと同じく、バージョン管理の対象である。

## 三つのバイアスと対策

判定器としてのLLMには、繰り返し観測されている偏りがある。MT-BenchやChatbot Arenaを扱った研究で整理された分類が実務でも使いやすい。

### Position Bias（位置バイアス）

対比評価で、提示された順序によって勝敗が変わる現象である。同じ二つの回答でも、先に出したほうが有利になる傾向が報告されている。

対策は単純で、順序を入れ替えて二回判定する。両方でAが勝てばAの勝ち、結果が食い違えば引き分けとして扱う。コストは倍になるが、これを省いた対比評価の数字は信用できない。

```python
import json

import anthropic

client = anthropic.Anthropic()

JUDGE_SYSTEM = """あなたは社内ナレッジ検索の回答を評価する審査員である。
与えられた検索文脈のみを根拠とし、次の観点で二つの回答を比較する。
1. 文脈に根拠のない主張を含まないこと（最重視）
2. 質問に正面から答えていること
3. 業務で使える具体性があること
回答の長さそのものは評価しない。長い回答が常に良いわけではない。
"""

SCHEMA = {
    "type": "object",
    "properties": {
        "reasoning": {"type": "string"},
        "winner": {"type": "string", "enum": ["A", "B", "tie"]},
    },
    "required": ["reasoning", "winner"],
    "additionalProperties": False,
}


def judge_once(question: str, context: str, answer_a: str, answer_b: str) -> str:
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=2000,
        system=JUDGE_SYSTEM,
        messages=[
            {
                "role": "user",
                "content": (
                    f"# 質問\n{question}\n\n# 検索文脈\n{context}\n\n"
                    f"# 回答A\n{answer_a}\n\n# 回答B\n{answer_b}"
                ),
            }
        ],
        output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
    )
    text = next(b.text for b in response.content if b.type == "text")
    return json.loads(text)["winner"]


def judge_pairwise(question: str, context: str, answer_a: str, answer_b: str) -> str:
    """順序を入れ替えて二回判定し、一致した場合のみ勝者を認める。"""
    first = judge_once(question, context, answer_a, answer_b)
    second = judge_once(question, context, answer_b, answer_a)
    # 二回目はAとBが入れ替わっているので読み替える
    swapped = {"A": "B", "B": "A", "tie": "tie"}[second]
    return first if first == swapped else "tie"
```

判定結果を構造化出力で受け取っている点にも触れておく。自由記述から正規表現でスコアを抜き出す実装は、フォーマット崩れのたびに欠損を生む。スキーマで縛れば、この種の失敗が消える。

### Verbosity Bias（冗長性バイアス）

長い回答を高く評価してしまう傾向である。中身が増えていなくても、説明を重ねただけで点が上がる。これは実害が大きい。プロンプトを「詳しく書け」と変えただけでスコアが上がり、改善したと誤認するからだ。

対策は三つ重ねる。第一に、評価プロンプトで長さを評価対象外だと明示する。上のシステムプロンプトの最終行がそれである。第二に、簡潔さを独立した指標として別に測る。第三に、回答の文字数を必ずログに残し、スコアと一緒に見る。スコアと文字数が同時に増えていたら、冗長性バイアスを疑う。

### Self-Enhancement Bias（自己増強バイアス）

判定器が、自分自身または同系列のモデルが生成した出力を高く評価する傾向である。

対策の基本は、生成に使うモデルと判定に使うモデルを分けることだ。ただし現実には、最も高性能なモデルを生成にも判定にも使いたい場面がある。その場合は、少なくとも次を守る。複数モデルによる判定を並走させて食い違いを監視する、リリース判定のような重い意思決定では人手評価を併用する、そしてモデル比較の結論は判定器を変えても同じかを確認する。

判定器を変えたら結論がひっくり返るような差は、そもそも意思決定に使える差ではない。

## ぶれを抑える実務的な手当て

バイアスとは別に、単純な判定のぶれがある。ここは地道な手当てが効く。

**Few-shotでアンカーを打つ。** 評価プロンプトに、採点済みの例を数件埋め込む。各点数の代表例を一つずつ置くのが効果的である。特に、判断に迷う境界の例——4点なのか3点なのか微妙な回答——を入れると、境界の位置が固定される。

**複数回判定して多数決を取る。** 温度を0にしても判定は完全には固定されない。重要な判定では3回走らせ、多数決を取る。ばらつきの大きさ自体も記録しておくと、そのルーブリックが曖昧かどうかの診断になる。3回とも違う点数が出るなら、直すのは回答ではなくルーブリックである。

**人間との一致度を測る。** 第1章で触れたとおり、判定器は定期的に校正する。50件から100件に人手ラベルを付け、コーエンのカッパ係数で一致度を出す。0.6を超えていれば実用域、0.4を割るなら評価プロンプトの作り直しを検討する、といった目安を持っておく。この校正は、評価プロンプトを変えたとき、判定器のモデルを更新したとき、対象ドメインが変わったときに必ず行う。

**判定できないという選択肢を残す。** 文脈が不足している、質問自体が曖昧、といった理由で採点できない件がある。無理に点を付けさせると、その分がノイズになる。`insufficient_information` のようなラベルを用意し、その比率も指標として監視する。比率が跳ねたら、データセットかアプリケーションのどちらかが壊れている。

> 評価器は、作った時点で正しいものではない。人間の判断と突き合わせて校正し続けて初めて、計測器になる。

::: tip この章のポイント
- 絶対評価は閾値判定に、対比評価はモデルやプロンプトの比較に向く。用途で使い分ける
- 絶対評価では連続値を避け、各点の意味を書き下した離散ラベルを使う
- 位置バイアスには順序入れ替えの二回判定、冗長性バイアスには長さの明示的な除外と文字数の記録で対処する
- 自己増強バイアスを避けるため、生成モデルと判定モデルは分ける。分けられない場合は複数判定器で検証する
- Few-shotのアンカー、多数決、判定不能ラベルの用意が、判定のぶれを実務的に抑える
- 判定器は人手ラベルとの一致度で定期的に校正する。校正なしの評価パイプラインは信用できない
:::
