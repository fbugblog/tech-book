# 第2章 RAGシステムの評価メトリクスと Ragas フレームワーク

RAGの評価でいちばんよくある失敗は、最終的な回答の良し悪しだけを一つのスコアで見ることである。回答が悪かったとして、検索が悪かったのか、生成が悪かったのかが分からない。分からないので、次に何を直せばいいのかも決まらない。

この章では、RAGを検索と生成に切り分けて測る指標体系を押さえ、Ragasで実際に計測するところまでを扱う。

## RAG Triad——三つ組で切り分ける

RAGの品質は、三つの要素間の関係として捉えると見通しがよい。質問、検索された文脈、生成された回答の三つである。この三つ組の各辺を測るという考え方は、TruLensがRAG Triadという名前で整理して広まった。

| 測る辺 | 問い | 失敗したときの症状 |
| --- | --- | --- |
| 質問 ↔ 文脈 | 引いてきた文脈は質問に関係しているか | 見当違いの文書を根拠に答える |
| 文脈 ↔ 回答 | 回答は文脈に基づいているか | ハルシネーション |
| 質問 ↔ 回答 | 回答は質問に答えているか | 話がずれる、要点に触れない |

三辺すべてが良ければ、そのRAGは質問に対して、根拠のある、関係した答えを返している。逆に、どの辺が落ちているかが分かれば、直す場所も決まる。Ragasはこの発想を、検索側と生成側それぞれ二つずつ、計四つの主要指標に具体化している。

## 検索性能を測る二つの指標

### Context Precision——引いてきた文脈の適合度

上位に並んだ文脈のうち、実際に回答へ寄与するものがどれだけ上に来ているかを測る。ランキングを考慮した精度であり、平均適合率の考え方に近い。

```
Context Precision@K = Σ_k (Precision@k × v_k) / （関連する文脈の総数）
```

`v_k` は k 番目の文脈が関連していれば1、そうでなければ0を取る。関連性の判定には、正解回答（reference）を使う方式とLLMに判定させる方式がある。

この値が低いとき、検索は必要な文書を引けてはいるが、ノイズを上位に混ぜている。リランカーの導入、チャンクサイズの見直し、メタデータフィルタの追加が対策になる。ノイズが多い文脈は、それ自体がハルシネーションの燃料になる点にも注意したい。

### Context Recall——文脈の網羅性

正解回答を構成する主張のうち、検索された文脈から導けるものの割合である。

```
Context Recall = （文脈に裏付けのある正解の主張数） / （正解の主張の総数）
```

計算に正解回答が必要なので、この指標だけはゴールデンデータセットなしでは測れない。裏を返せば、Context Recallを測りたいという動機が、データセットを整備する最も強い理由になる。

値が低いときは、そもそも必要な情報が検索段で落ちている。チャンク分割で文脈が断ち切られていないか、埋め込みモデルが日本語のドメイン語彙を捉えられているか、検索件数 k が小さすぎないかを疑う。生成側をいくら調整しても、ここが落ちている限り回答は良くならない。

## 生成性能を測る二つの指標

### Faithfulness——忠実性

回答が文脈に忠実かどうか、すなわちハルシネーションの少なさを測る。計算は二段階で行う。

1. 生成された回答を、個々の主張（claim）に分解する
2. 各主張について、与えられた文脈から導けるかどうかを判定する

```
Faithfulness = （文脈から導ける主張の数） / （主張の総数）
```

回答全体をまとめて「正しいか」と問わず、主張単位に割るのが要点である。一文の中に正しい部分と根拠のない部分が同居していても、割合として現れる。

実務上の閾値としては、社内ナレッジ検索で0.85前後、金融や医療のように誤情報のコストが高い領域では0.95以上を目標に置くことが多い。ただしこの数値は評価器モデルと分解の粒度に依存する。他社の公開値と自分たちの値を直接比べても意味はない。自分たちのデータで基準線を引き、そこからの変化を見る。

### Answer Relevancy——回答の関連性

回答が質問に答えているかを測る。仕組みがやや変わっていて、回答から質問を逆生成する。

1. 生成された回答から、その回答が答えになりそうな質問を n 個作る
2. 逆生成した質問と元の質問の埋め込み類似度を計算する
3. その平均を取る

回答が焦点を外していれば、そこから逆生成される質問は元の質問から遠ざかる。この指標は事実の正しさを見ていない点に注意してほしい。正しくない回答でも、質問に正面から答えていれば高い値が出る。Faithfulnessと組み合わせて初めて意味を持つ。

なお、この計算には埋め込みモデルが必要である。日本語で評価する場合、埋め込みモデルの日本語性能がそのままスコアに効いてくる。

## Ragasで実際に測る

四つの指標を実際に走らせる。評価器のLLMと埋め込みモデルを明示的に渡すのが実務上の要点である。既定値に任せると、評価器が変わったことに気づかないままスコアが動く。

```python
from datasets import Dataset  # 参考: ragas は list[dict] からも組める
from langchain_anthropic import ChatAnthropic
from langchain_huggingface import HuggingFaceEmbeddings
from ragas import EvaluationDataset, evaluate
from ragas.embeddings import LangchainEmbeddingsWrapper
from ragas.llms import LangchainLLMWrapper
from ragas.metrics import (
    Faithfulness,
    LLMContextPrecisionWithReference,
    LLMContextRecall,
    ResponseRelevancy,
)

# 評価器は固定する。ここを動かすとスコアの比較可能性が失われる
evaluator_llm = LangchainLLMWrapper(
    ChatAnthropic(model="claude-opus-5", temperature=0, max_tokens=4096)
)
evaluator_embeddings = LangchainEmbeddingsWrapper(
    HuggingFaceEmbeddings(model_name="intfloat/multilingual-e5-large")
)

samples = [
    {
        "user_input": "有給休暇の付与日数は勤続何年で最大になりますか",
        "retrieved_contexts": [
            "勤続6年6か月以降、年次有給休暇の付与日数は20日で上限となる。",
            "年次有給休暇は入社6か月経過時点で10日付与される。",
        ],
        "response": "勤続6年6か月以降に20日で上限となります。",
        "reference": "勤続6年6か月以降、付与日数は20日で上限となる。",
    },
]

dataset = EvaluationDataset.from_list(samples)

result = evaluate(
    dataset=dataset,
    metrics=[
        LLMContextPrecisionWithReference(),
        LLMContextRecall(),
        Faithfulness(),
        ResponseRelevancy(),
    ],
    llm=evaluator_llm,
    embeddings=evaluator_embeddings,
)

print(result)
df = result.to_pandas()  # 件ごとのスコアを見て、低い行を読む
```

出力された平均値を眺めて満足してはいけない。`to_pandas()` で件ごとのスコアに落とし、下位の数件を実際に読む。この作業から得られる示唆が、平均値の増減より圧倒的に多い。低い行には、たいてい設問の不備か、チャンク分割の破綻か、指示の曖昧さが具体的な形で現れている。

## ゴールデンデータセットを合成する

評価の最大のボトルネックは、指標ではなくデータである。数百件の質問と正解を人手で作るのは重い。Ragasはここに、対象ドキュメントから評価用データセットを自動生成する機能を持っている。

内部では、文書群からナレッジグラフを構築し、そこに複数のクエリ合成器を適用する。単一の文書片から答えられる質問、複数の文書をまたがないと答えられない質問、抽象度の高い質問といった種類を、指定した比率で混ぜられる。

```python
from langchain_community.document_loaders import DirectoryLoader
from ragas.testset import TestsetGenerator

docs = DirectoryLoader("./corpus", glob="**/*.md").load()

generator = TestsetGenerator(llm=evaluator_llm, embedding_model=evaluator_embeddings)
testset = generator.generate_with_langchain_docs(docs, testset_size=50)

testset.to_pandas().to_csv("golden_dataset_draft.csv", index=False)
```

ファイル名を `draft` にしてあるのは意図的である。合成データセットはそのまま使わない。次の三点を人間が通す。

- **正解が本当に正解か。** 元文書の記述が古い場合、生成された正解も古い。
- **質問が実際の利用者の言い回しか。** 合成された質問は文書の語彙に引きずられ、整いすぎる傾向がある。現場では「有休って何日たまるんだっけ」と聞かれる。
- **答えられない質問が入っているか。** 合成器は答えられる質問ばかり作る。文書に情報がなく「分かりません」と答えるのが正解の設問を、意図的に一割ほど足す。この種のケースを入れないと、ハルシネーション耐性がまったく測れない。

このデータセットは、アプリケーションのコードと同じリポジトリでバージョン管理する。データセットを更新したらスコアが動くのは当然なので、更新はアプリケーションの変更と同じコミットに混ぜず、単独のコミットで基準線を引き直す。

## 指標を運用に載せるときの注意

三つだけ書き添えておく。

第一に、スコアの絶対値を目標にしない。「Faithfulness 0.9以上」を最初から掲げるのではなく、まず現状を測って基準線を引く。意思決定に使うのは変化量である。

第二に、評価にもコストがかかる。四指標をLLMで計算すると、1件あたり数回から十数回のAPI呼び出しが発生する。500件のデータセットなら、一回の評価で数千回だ。日常のCIでは部分集合、夜間やリリース前に全件、という二段構えにする（第3章で扱う）。

第三に、評価の実行自体も不安定である。評価器の出力がパースできずに欠損になる件が出る。欠損率も併せて記録し、極端に高い場合はスコアの比較を止める。

::: tip この章のポイント
- RAGは質問・文脈・回答の三つ組の各辺を測ると、検索と生成のどちらが原因かを切り分けられる
- Context Precisionはノイズの混入、Context Recallは情報の取りこぼしを検出する
- Faithfulnessは回答を主張単位に分解して根拠の有無を測り、ハルシネーション率の代理指標になる
- Answer Relevancyは回答から質問を逆生成して測る指標で、事実の正しさは見ていない
- Ragasの合成データセットは出発点であり、正解の検証・言い回しの現実化・答えられない質問の追加を人間が行う
- 評価器モデルとデータセットは固定し、スコアの絶対値ではなく変化量で意思決定する
:::
