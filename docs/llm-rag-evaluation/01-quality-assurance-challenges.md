# 第1章 LLMアプリケーションにおける「品質保証」の課題

社内文書を検索して答えるRAGアプリケーションが動き始めたとする。手元でいくつか質問を投げてみて、どれも悪くない答えが返ってきた。ここでプロンプトを少し直したくなる。直したあと、あなたはどうやって「悪化していない」と確かめるのだろうか。

この章では、確率的に振る舞うシステムに品質保証という言葉をどう当てはめるのかを整理する。ここが曖昧なままだと、後続の章で扱うメトリクスもCIも、ただの数字遊びになってしまう。

## テストの前提が崩れている

従来のソフトウェアテストは、決定論の上に成り立っている。同じ入力に同じ出力が返ることを前提に、期待値との一致を検証する。

```python
def test_add():
    assert add(2, 3) == 5
```

この一行が機能するのは、`add(2, 3)` が未来永劫5を返すからだ。LLMではこの前提が二重に崩れる。

一つ目は、生成そのものが確率的である点だ。温度を0に設定しても出力は完全には固定されない。GPUの並列演算における浮動小数点の加算順序、混合エキスパートモデルにおけるバッチ構成の影響、推論サーバーの実装差といった要因で、同じリクエストが別のトークン列を生むことがある。

二つ目は、正解が一つではない点だ。「返品は購入後30日以内に受け付けています」と「ご購入から30日以内であれば返品を承ります」は、文字列としては別物だが、業務上はどちらも正解である。完全一致はもちろん、BLEUやROUGEのような表層的な類似度も、この同値性をうまく扱えない。

| 観点 | 従来のソフトウェア | LLMアプリケーション |
| --- | --- | --- |
| 出力 | 決定的 | 確率的 |
| 正解 | 一意 | 複数の表現が同値 |
| 判定 | 期待値との一致 | 基準に対するスコア |
| 単位 | 1件のアサーション | データセット全体の分布 |
| 失敗 | ビルドが赤くなる | 平均スコアが閾値を下回る |
| 原因追跡 | スタックトレース | トレースとメトリクスの内訳 |

結論はシンプルである。テストの単位を1件から集合へ移し、判定を一致からスコアと閾値へ移す。100件の評価データセットに対して忠実性の平均が0.85を下回ったら失敗、といった形に書き換える。

> テストの単位を1件から集合へ、判定を一致からスコアと閾値へ。この二つの置き換えが、LLMの品質保証の出発点になる。

## 壊れ方には型がある

「なんとなく精度が悪い」という報告は改善につながらない。RAGの壊れ方は、パイプラインの構造に沿って分類できる。

### ハルシネーション（根拠のない生成）

検索してきた文書に書かれていないことを、モデルが埋めてしまう現象である。RAGにおけるハルシネーションの多くは、生成モデルの暴走というより検索の失敗の帰結だ。関連文書が引けていない状態で「分かりません」と言わずに答えようとすると、モデルは事前学習の知識や文脈の断片から、もっともらしい文を組み立てる。

だから対策も二段になる。検索側では網羅性を上げる。生成側では、根拠の外に出た主張の割合を測り、閾値を超えたら止める。この「根拠の外に出た主張の割合」が、第2章で扱うFaithfulnessである。

### 関連性の欠如

事実としては正しいが、聞かれたことに答えていないパターンである。「解約の手続きは」と聞かれて、解約に関する一般論を長々と述べて肝心の手順に触れない回答がこれにあたる。ハルシネーションとは独立に起きるので、独立した指標で測る必要がある。

### 情報漏洩

RAGに固有の、最も事業リスクが大きい壊れ方である。漏洩の経路は三つある。インデックス作成時に権限外の文書を取り込んでしまう経路、検索時に利用者の権限フィルタを通さずに文書を引いてしまう経路、そして出力の中に個人情報や機微情報がそのまま現れる経路だ。

前の二つは検索段の問題であり、LLMの評価ではなくアクセス制御のテストで潰す。評価データセットには「権限のない利用者として権限外の文書に関する質問を投げ、その文書が検索結果に含まれないこと」を検証するケースを必ず入れておく。三つ目は出力側の検知であり、第5章のガードレールが担当する。

## 評価の3大アプローチ

測るべき対象が決まったら、次は誰が測るのかを決める。選択肢は三つある。

| アプローチ | 中身 | 長所 | 短所 |
| --- | --- | --- | --- |
| Human Evaluation | 人が読んで採点する | 最も信頼できる。業務文脈を反映できる | 遅い。高い。評価者間でぶれる |
| Heuristic Rules | 正規表現、文字数、JSONスキーマ、禁止語リスト | 速い。安い。完全に再現する | 意味を判定できない |
| LLM-as-a-Judge | 別のLLMに採点させる | 意味を判定できる。スケールする | コストがかかる。バイアスがある |

実務では、この三つを排他の選択肢として扱わない。三層に積む。

第一層はヒューリスティックである。JSONとしてパースできるか、禁止語を含んでいないか、応答が空でないか、想定を超える長さになっていないか。この種の判定にLLMを使うのは無駄であり、CIの最初の数秒で落とすべき類の失敗だ。

第二層がLLM-as-a-Judgeで、忠実性や関連性といった意味の判定を担う。データセット全体に対して自動実行できる唯一の現実的な手段である。

第三層が人手評価だが、ここでの位置づけが重要である。人手評価は全件を見るためのものではなく、判定器を校正するためのものだ。50件から100件程度に人間のラベルを付け、LLM判定器のスコアとの一致度を測る。一致度が低ければ、まず直すべきはアプリケーションではなく評価プロンプトの側である。

一致度はコーエンのカッパ係数などで数値化しておくとよい。この「評価器を評価する」工程を省くと、以降のスコアはすべて宙に浮く。

## 評価はテストではなく計測器である

最後に、言葉の整理をしておきたい。LLMの評価は、合否を出すテストというより、同じ条件で繰り返し当てられる計測器に近い。

計測器としてまず求められるのは、絶対値の正確さではなく、比較の一貫性である。忠実性0.87という数字そのものに意味はない。プロンプトAで0.87、プロンプトBで0.79という差分にこそ意味がある。だから評価器のモデル、評価プロンプト、データセットは固定し、被測定対象だけを動かす。三つを同時に変えた実験は、何も測っていないのと同じだ。

この視点に立つと、品質保証の作業は次の四つに分解される。第2章以降で、順に埋めていく。

1. 何を測るかを決める（メトリクスの定義）
2. 何に対して測るかを揃える（評価データセット）
3. いつ測るかを決める（CIとリリースゲート）
4. 本番で測り続ける（オブザーバビリティとフィードバック）

::: tip この章のポイント
- LLMは出力が確率的で正解も一意でないため、期待値との一致によるテストが成立しない
- テストの単位を1件からデータセット全体へ、判定を一致からスコアと閾値へ置き換える
- RAGの壊れ方はハルシネーション・関連性の欠如・情報漏洩に分類でき、それぞれ対処する層が違う
- 評価はヒューリスティック、LLM-as-a-Judge、人手の三層で積む。人手評価は判定器の校正に使う
- 評価は計測器であり、意味を持つのはスコアの絶対値ではなく条件を揃えた差分である
:::
